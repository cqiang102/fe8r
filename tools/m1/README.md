**偏差的主要来源是"未分类 2911 → 0"**：§2.6 的那 2911 个本来就没有归属，
M1 把它们分掉了，所以规则层和表现层必然变大。这不是矛盾，是同一件事的两面。

平台层减少则是因为本轮**只认"定义级"证据**（见下），而 §2.6 的口径更宽。

> §2.6 自己就写了：「分类是启发式的，精确清单需要 M1 的一次系统归类」。
> 所以那张表是量级参考，不是验收标准。**本轮的验收标准是 D19 的未分类为 0。**

## 方法：五级判定

从强到弱，每一级都记录"是哪条规则判的"，结果可审计。

| 级 | 判据 | 说明 |
|---|---|---|
| **A** | 空函数 | `nullsub_*` 且函数体为空 → 舍弃（只为占 ROM 地址） |
| **B** | **决定性特征** | §4.8 N1–N10 的符号特征 |
| **C** | 调用图传播 | 被谁调用——文件在依赖图里的位置 |
| **D** | 弱特征 | 改游戏状态 vs 写硬件/显存 |
| **E** | 名称语义 | 文件名**与函数名** |
| **F** | 兜底 | 全都没命中 → 判 port，标 `low` 置信度 |

### 三个把准确率拉起来的关键区分

这几条都是**实测踩坑之后**才总结出来的，值得单独记：

#### 1. 「定义子系统」≠「调用子系统」

早期版本用 `\bDecompress\b` 判平台层，命中 285 个文件——
但绝大多数只是在**解压贴图**，它们不是压缩算法。
`MPlayStart`（放个音乐）、`SioSend`（发个包）同理。

于是整个平台层虚高到 1038（估算 485），而且 `ADJUSTFROMXI_MoveCameraOnSomeUnit.c`
这种相机函数被判成了平台层。

**做法**：只有当文件**自己定义**了该子系统的函数时，才算证据。
调用不算。

#### 2. 「决定性特征」≠「提示性特征」

`Proc` 是这套分类法里最大的陷阱：**1301 个文件引用它，但两层都用**——
AI 决策和事件引擎也拿它当控制流。

只按"是否出现 Proc"判定时，331 个规则层文件会被误判成"重写"：

```
AiEscapeAction.c       → 规则层（AI 决策）
CpDecide_Main.c        → 规则层（AI 决策）
CpPerform_EquipBest.c  → 规则层（AI 决策）
```

这些一旦判错，**AI 行为直接丢失**。

**做法**：把特征分成两级——

- **决定性**：只有这一层才会**定义**的东西
  `ProcScr_`（定义一段演出时序）是表现层；`Proc_Start`（用协程跑逻辑）不是。
  `BattleGenerate`（战斗公式）是规则层；`NextRN`（取个随机数）不是。
- **提示性**：两层都可能用的通用设施，只做加权，不单独定性。

#### 3. 优先级是「平台 > 规则 > 表现」

规则排在表现前面是刻意的：**漏掉一条规则比多写一份 UI 严重得多**。
一个文件若同时定义了战斗公式和一段演出，它必须进移植队列。

同理，兜底层默认判 **port** 而不是 rewrite。但要强调的是——
**「有结论」和「有把握」是两件事**：兜底的文件全部带 `low` 置信度标记，
进复核清单，不会被悄悄埋掉。

#### 4. 语义在函数名上，不在文件名上

大量文件按 ROM 地址命名：

```
src/exact_08005c68.c   →   void FaceBgBlink_Init(struct FaceBlinkProc* proc)
src/exact_08009588.c   →   void AP_ExecDummyFrame(struct APHandle* handle)
```

`exact_` / `masked_` / `sub_` / `nullsub_` 是**匹配状态**前缀，不是语义。
所以名称规则必须同时作用于**文件名和文件里定义的函数名**。

### 关于 Proc 匹配宽度的一次教训

`\bProc_Start\b|\bProc_Find\b|\bPROC_REPEAT\b|\bPROC_END\b` 看起来够用，
实际漏掉了 `Proc_Break`（151 个文件）、`Proc_EndEach`、`Proc_StartBlocking`、`ProcPtr`。
Proc 是本项目覆盖面最大的单一特征，**宁可宽一点**。

## 风险与残余不确定度

**408 个低置信度文件**需要复核。其中真正危险的是那 5 个风险文件。

复核顺序建议：

1. `risk_state=yes` 的 5 个（会丢规则）
2. `layer=port 且 confidence=low` 的 372 个（可能是白费功夫的 UI）
3. `layer=rewrite 且 confidence=low` 的 36 个

复核方式是读 C 源码判断"做什么"归属哪层，结论写回 `NAME_RULES` 或
`FEATURES`，然后重跑——**分类器是代码，不是一次性表格，改完能立刻重算**。

## 下一步

M1 的产出让 §7 的任务派发有了硬性守卫：

- `layer=port` 的文件才进移植队列
- `layer=rewrite` 的文件不进"翻译"队列，而是走设计流程
- `layer=discard` 的文件直接跳过——**这正是 §4.8 存在的意义**：
  防止 AI 去"移植" 1301 个 Proc 文件、311 个 OAM 文件
