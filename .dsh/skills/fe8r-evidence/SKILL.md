# 什么算证据

这个仓库的 12 个真实 bug **没有一个报错**，全都是"跑起来了，但不对"。
而当时的判据一直是"我盯着截图看" —— **截图只覆盖那一刻那一帧**。

## 1. 完成的口径

**只有存在可重复执行的检查，才能说「完成」。** 否则用别的词。

报状态时**分四类**，不许让第一类吸收后三类：

```
机器验证   —— 有测试/门禁/转储断言钉住
抽查过     —— 看过一次，没有可重复检查
未验证     —— 没看过
已知有 bug —— 知道它坏了，写清楚坏在哪
```

反例（都真实发生过）：

| 当时宣称 | 实际证据 | 真实口径 |
|---|---|---|
| 开场链路 OK | 难度页 1 张截图 | 难度页抽查过；链路未验证 |
| 序章剧情 OK | 过场某几句的截图 | 过场未验证能走完 |
| 序章战斗 OK | 一次攻击的截图 | 未验证能重复打赢 |

**明确列出"我没看过的地方"。**"其他应该没问题"不是可接受的回答。

## 2. 优先用状态转储，而不是看图

`FE8R_DUMP=<path>` 出 JSON 状态转储。它比截图强的地方是**一次跑回答多个问题**：

```
单位 id 唯一: True    渲染组件数: 6    单位数: 5     ← 6 ≠ 5，有幽灵精灵
EIRIKA items=[108]                                 ← 只有伤药，没拿到细剑
地图历史: Ch16Map PrologueMap                       ← ✓
```

**这两条我自己看截图永远发现不了 —— 转储一次就抓到了。**

写断言时优先加这两条（会当场抓到 id 冲突与幽灵精灵）：

```dart
assert(field.units.map((u) => u.id).toSet().length == field.units.length);
assert(_unitById.length == field.units.where((u) => u.isAlive).length);
```

## 3. 截图仍然有用，但要按它的规矩用

```bash
./tools/verify/shot.sh <out.png> [标题画面] [输入脚本]
```

* 环境变量：`FE8R_DEBUG=1` 显示调试 HUD；`FE8R_TITLE=` 跳到某个画面；
  `FE8R_SCRIPT="confirm,confirm,wait,confirm"` 给输入脚本。
* **`stat -f%z` 比字节数**：与改动前**字节完全相同 ⇒ 改动没生效**，
  先查这个，再从图里下任何结论。抓到过两次
  （`..anchor = Anchor.topLeft` 是空操作；`FE8R_NODELAY` 制造的假象）。
* **分阶段停点**：别一次跑到底。停在"动作菜单该弹出的那一刻"看 HUD，
  就能区分"菜单没弹"和"菜单弹了但后续没走通"。
  这一招把「攻击没执行」纠正成了「其实是脚本时序问题」。
* **两边的依据都显示出来**：数据与画面不一致时（HUD 坐标 vs 光标实际位置），
  不要信任你能打印的那一半。单位 id 冲突那次，HUD 坐标一直是对的，
  **错的是画面** —— 我盯着对的那一半看了好几轮。

## 4. 门禁绿 ≠ 门禁有效

**新增或修改任何一条规则/断言后，必须验证它真的会失败**（造一个违规样本，看它红）。

真实教训：`check_architecture.dart` 的 R7（要求 `PORT OF:` 头注释）
因为用了剥注释的作用域，而它要匹配的正是注释 ——
于是"出现在任何合法 Dart 里都不可能命中"。审计实测：新建一个没有 `PORT OF:`
的纯文件，门禁仍报「7 条规则通过」、退出 0。**这条规则假了很久。**

反例还有：`run_all.dart` 曾经在空仓库上跑也报「通过 27 项」、退出 0。

## 5. 别让工具自己制造结论

**你新加的调试开关可能制造出你随后当成发现的那个假象。**

真实事故：为了让长过场跑完，我加了 `FE8R_NODELAY`（把输入间隔压到 0）。
它把 3000 个 confirm 在**场景开始之前**就丢光了，画面于是停在"过场还没开始"：
没有对白框、脚本名 `[-]`、地图还是上一张。**我把它读成了"过场跑完了"**，
据此得出「`loadMap(0)` 从未执行」的结论，**还写进了提交信息**。

规则：改动/新增了测试设施后，先用一个**独立判据**确认它没有改变被观察对象。

## 6. 用户说"不对" = bug 报告

**先当"存在 bug"去构造判据，不要先解释"应该是对的"。**

实测 6 次「不对」（单位 / 剧情移动 / 按源码做 / 光标 / 我方显示 / 相机），
**6 次全中**，每次都指向一个真 bug。第一反应常常是解释"应该是对的" —— **顺序反了。**

## 7. 判据红的正确读法

测试红了**先怀疑"是不是数据真的变了"**，而不是"测试坏了"。

真实收益：`unit_defs_test`（125→406 张表）、`chapter_loader_test`（8→15 章）、
「没有敌军」那条测试甚至自己在注释里写着"这句失败说明数据补齐了，那时应当删掉这个测试"。
**这些红都是数据真的变了，不是测试坏了** —— 逐个核实后再更新。

## 8. 报告的门槛

* 涉及项目数据的每句话都要能指到 `file:line`；指不到就写「**未查证**」。
* 卡住了就说**卡在哪一条判据**上，不要用"差不多了"收尾。
* 「找到一个可疑的东西」≠「找到了原因」。
  反例：`Event_TextWithBG` 缺失被当成了根因，验证后**不是**
  （`Scene.call` 对缺脚本是优雅返回的）。
