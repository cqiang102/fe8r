## 二、老是犯错的模式

### 把 12 个真 bug 排出来，会发现**它们是同一件事**

| # | Bug | 我当时的做法 |
|---|---|---|
| 1 | `MNC2` 是占位符 → 永远停在序章 | 没查 `EvtChangeChapterBM` |
| 2 | `LoadUnits` 只写 HUD 字符串 | 没查 `LOAD1` 该干什么 |
| 3 | `MOVE` 只写 HUD 字符串 | 没查 `EvtMoveUnit` |
| 4 | `WANTED_SCALAR = ("number",)` → 职业无属性 | 没查 `struct ClassData` 有哪些字段 |
| 5 | `number` 是枚举名 → 索引全空 | 没查 `data_items.c` 写的是什么 |
| 6 | `allegiance` 1=绿，我以为 1=红 | **想当然** |
| 7 | `LOMA` 少调 `RestartBattleMap()` | 没查 `eventscr_0800F390.c` |
| 8 | 单位 id 撞车 → 我方被顶掉 | 没想过 id 要唯一 |
| 9 | 提取器只扫三个目录 → 少 2/3 的表 | 靠**猜目录名** |
| 10 | `glob` 少 `recursive=True` | 不知道 `**` 不递归 |
| 11 | `.byte`/`.4byte` 混在一个 list | 没看两种指令的区别 |
| 12 | `_followCursor` 是我**自己发明**的 | 没查 `HandleMoveCameraWithMapCursor` |

**一句话：我写的是「看起来合理的实现」，而不是「源码里的实现」。**

### 四个更深的模式

**① 静默失败**
这 12 个 bug **没有一个报错**。全都是"跑起来了，但不对"。
最危险的是 ④⑤：战斗**悄悄退回演示数据**，界面上一切正常。

**② 用「数字对」自我安慰**
修 id 冲突那次最典型：HUD 一直显示正确的坐标，我就以为没问题 ——
**而错的是画面，不是数字**。我盯着对的那一半看了好几轮。

**③ 我自己造的工具把我骗了**
`FE8R_NODELAY` 是我为了"推长过场"加的，结果它把输入在场景开始前就丢光了，
我却据此得出「`loadMap(0)` 从未执行」的**错误结论**，还写进了提交信息。

**④ 找到"一个可疑的东西"就当成"找到了原因"**
`Event_TextWithBG` 缺失 → 我怀疑它是根因。后来验证：**不是**
（`Scene.call` 对缺脚本是优雅返回的）。
我当时写了"因果还没坐实"，但语气上已经把它当成结论了。

**⑤ 记错事实还当事实叙述**
我说了好几轮"艾莉卡在 (13,9)" —— 那其实是**赛特**。
源码一直是 `charIndex=0x02`(SETH)。**提取没错，是我叙述错了。**

### 而有效的技术，全部是**判据**

| 判据 | 抓到的东西 |
|---|---|
| **截图字节完全相同 ⇒ 改动没生效** | `Anchor.topLeft` 空操作、`FE8R_NODELAY` 假象 |
| **字节数严丝合缝** | 事件脚本解码（12 条命令 / 13 字）|
| **把两边的依据都显示出来** | 单位 id 冲突（HUD 坐标 vs 光标位置）|
| **指令轨迹（最近 N 条）** | 「场景停在第 2 条指令」|
| **分阶段截图**（停在中途） | 动作菜单其实弹出来了（是脚本时序问题）|
| **用美版 C 交叉验证日版字节** | 解码正确性；还发现美版坐标不同 |
| **测试红了是好事** | 125→406 张表、8→15 章、"没有敌军"变"有敌军" |
| **「正向判据」而非「没崩」** | `byNumber` 长度 > 200（索引没空）|

### 最后一条，也是最有效的

**用户的眼睛。** 你报了 6 次「不对」：
单位不对 / 剧情不动 / 按源码做 / 光标不对 / 我方不对 / 相机不对 ——
**每一次都指向一个真 bug，没有一个是我多虑。**

而我的第一反应常常是解释「应该是对的」。**这个顺序反了。**

## 三、怎么改：把「靠自觉」变成「靠机制」

### A. 让"没接上源码"变成 CI 失败（最高价值）

**已经被证明有效的一条**：`check_architecture.dart` 的 R7 要求
`lib/core` 每个文件有 `PORT OF:` 头 —— 它已经拦过我一次。

**要加的**：

1. **占位符棘轮**：`s.placeholder(...)` 的数量只许降不许升。
   现状 16。CI 记录数字，**变大就红**。
   （这直接对应 bug ①②③）
2. **禁止硬编码的游戏数值**：`lib/game` 里出现 `classId: 0x2A` 这类字面量就红。
   （对应 bug ④⑤）
3. **每个提取器输出后做"正向抽查"**：
   不是"文件存在"，而是"`CLASS_EIRIKA_LORD.baseDef == 3`"。
   （对应 bug ④⑤⑨）

### B. 静默失败必须响亮

1. **查表失败要抛**（debug 模式）或**写进一条必红的测试**，不是写 HUD。
2. **`_addUnits` 后断言**：单位真的落在 `field.units` 里、id 真的唯一。
   （对应 bug ⑧）
3. **`BattleView` 断言**：`_unitById.length == field.units.where(alive).length`。
   （这条会**当场**抓到 id 冲突）

### C. 判据先于实现

**规则**：动代码之前，先写下「什么可观测的东西能证明我做对了」。
提交信息里**必须**带这一行。

这次做得好的例子就是提交 `c2caaf6`（"含严丝合缝判据"）——
判据写在标题里，后来一路受用。

### D. 先搜源码，再写代码

1. **`docs/源码索引.md` 扩成「功能 → 源文件」的索引**，
   写任何玩法逻辑前先查它。
2. **没有 `PORT OF:` 就不许写** —— 把 R7 从 `lib/core` 扩到 `lib/game`。

### E. 禁止"用字符串切片改代码"

我用 `s.index(...)` + 切片删掉了 `_loadSceneData()` 和 `backgroundColor()`，
靠"编译不过"才发现。**如果删掉的是不报错的东西就会静默损坏。**
→ 一律用 `edit` 的精确替换。

### F. 事实必须带出处

**规则**：任何关于项目数据的陈述，都要能指到 `文件:行`；
指不到就标注「**未查证**」。
（对应"艾莉卡/赛特"那次）

### G. 删掉会骗人的工具

`FE8R_NODELAY` 已经没有正面价值（它制造了假象）。
**要么删，要么在名字和输出里标明"这个模式会丢输入"。**
→ 已确认：它只在"场景开始前"丢输入。**应当删掉。**

### H. 用户的观察优先

**规则**：用户说"不对" → **先当成"存在 bug"去构造判据**，
而不是先解释"应该是对的"。
这次 6 次全中，说明**用户的观察比我的自检可靠**。

---

## 四、一句话

**这 12 个 bug 里，没有一个是"算法难"，全部是"没读源码 / 没设判据"。**

所以改善的方向不是"更小心"，而是**把判据做成机器执行的**：
* 没接源码 → CI 红
* 静默失败 → 断言红
* 数字对但画面错 → **两边的依据都显示出来**

## 三个"工具在撒谎"的新教训

**① 指标分不清自己在数什么，就会制造假 bug 报告。**
上一轮我把 `componentCount = 6`（= 5 个单位 + 1 个光标）读成"有幽灵精灵"，
**还当成一个发现报告了**。指标现在拆成
`unitComponents / markerComponents / cursorComponents`，判据只比第一项与存活单位数。

**② 一个恒为真的字段比没有字段更糟。**
`scene.running` 原来写的是 `sc != null` —— 场景对象一加载就非空，
这个字段**永远是 true**，看起来像"场景在跑"，实际什么都没说。
现在它读的是真的 `_sceneRunning`。

**③ 转储自己也会静默失败。**
`slots` 的键写成了 int，`jsonEncode` 编不了 —— 而**只有槽非空时才炸**：
标题画面那会儿转储正常，一到序章（脚本真的用了槽）整个转储失败。
要命的是 `scenario.sh`/`shot.sh` 的输出被 `grep` 过滤过，
`[dump] 失败` 那行看不见，我只能靠"文件不在"猜到。
现在：**转储缺失 = 失败**，报错行会打出来。
（这类"跑 60 秒才知道"的事，现在有一条 1 毫秒的测试：
`dumpState()` 必须可 JSON 编码，且槽非空。）

## 这一轮做成的机制（都带证伪）

| 机制 | 判据 | 证伪方式 |
|---|---|---|
| **占位符棘轮** | `placeholder` 调用点 / op 名 / 缺失脚本，任一变大即红 | 往生成物里加 2 个占位 → 红（3757→3759）；`--selftest` 也验 |
| **转储判据**（14 条）| id 唯一 / 渲染数==存活数 / 5 槽 / 坐标 / 相机 / 细剑 / 名册 / 场景跑完 | `--selftest` 喂 6 个**故意坏掉**的转储，要求每条都被抓到 |
| **端到端场景** | `scenario.sh prologue` → 真机转储 → 判据 | 放进 `--e2e`（默认不跑，**默认的"通过 N 项"不含它**）|
| **`loadRuleData()` 拆出来** | 规则层数据可单测 | 原来整条 `onLoad` 在 widget test 里**走不完**（图片解码），bug 只能靠肉眼 |

## 还有一条：**提交信息里的数字也是断言**

我写完提交信息后去核对门禁输出，发现自己写的「41 项」实际是 **40 项**（41 是
带 `--e2e` 的数）。已经改掉重提交。
**凡是我写下的数字，都要来自刚跑过的输出，不能来自"应该差不多"。**

## 三处用户报告的根因（一句话）

```
开场链路  →  tick() 接在按键上（时间是帧驱动的）
序章剧情  →  道具栏 1 个元素（UnitAddItem 永远失败）→ 艾莉卡没武器

# 附录三：继续修 `CAMERA` 时又挖出一个（第 23 个）

| # | Bug | 形状 |
|---|---|---|
| 23 | `update()` 里"相机每帧跟光标"**过场里也在跑** | 把 `LOMA`/`CAMERA` 设好的镜头每帧拖回玩家光标处 |

补上 `CAMERA(x, y)` 之后转储给出 `camera=(48, 0)`，而按源码算应该是 `(96, 0)`：

```
LOMA(0x10)   → GetCameraCenteredX(14*16) = 96
CAMERA(14,0) → GetCameraAdjustedY(0)     = 0     （y 顶到王座）
             → GetCameraAdjustedX(96,224) = 96    （x 在死区内，不动）
```

96 → 48 的来源：`GetCameraAdjustedX` 的右分支 `224 - 176 = 48`，
也就是**相机当时在 0**。谁把它挪到 0 的？每帧的光标跟随：

```dart
if (state != null && !inTitleFlow) _handleMoveCameraWithMapCursor(4);
```

玩家光标停在 (2,2)，相机在 96 → `96 + 48 > 32` → `camera.x = 0`。

出处：`HandlePlayerCursorMovement` 的调用点是 `PlayerPhase_MainIdle`
（`src/playerphase_0801C5A8.c:62`）—— 事件演出期间**没有这一步**。

**两条 bug 叠在一起，症状都是"取景不对"。**

## 这一轮最值钱的一条：**同一个指令，四种参数形状**

```c
#define MOVE(speed, pid, x, y)             EvtMoveUnit(...)
#define MOVEONTO(speed, pid, pid_target)   EvtMoveUnitToTarget(...)
#define MOVE_1STEP(speed, pid, direction)  EvtMoveUnitOneStep(...)
#define MOVE_DEFINED(pid)                  EvtMoveUnitByQueue(...)
```

引擎里是**同一个** `Event2F_MoveUnit` 按子命令分派（`src/sub_800FF08.c:55-110`）。
我按第一种的形状读了全部四种 —— 于是三次移动里两次走到错格子、一次根本没动。

**教训：看到一族同前缀的宏，先去读它们的定义，别拿一个样本推其余。**

# 附录五：把序章打到第 1 章（第 26、27、28 个 bug）

目标：**在真机里从开机一路玩到第 1 章**。为此先补了 START 跳过
（`EV_STATE_SKIPPING`，`src/event_0800D110.c:27`），然后一段固定输入脚本打过去。
一路撞出三个"不报错、但整条链不走"的 bug：

| # | Bug | 为什么它不报错 |
|---|---|---|
| 26 | 单位编号从 `0x100` 起 → 超出**阵营区块** | `GetPhaseAbleUnitCount` 是**按 id 区间**数的（`for (id = faction+1; id < faction+0x40; id++)`），编号跑出区块 → 敌方阶段被当成"没人能动"直接跳过 → AI 一步不走。回合数照涨 |
| 27 | `terrainBonuses` 返回 `(avoid, defense)`，调用点按 `(def, avo)` 解构 | 位置记录解构**顺序错了不报错**，只是数字反了：山峰的 40 回避当成防御 → 伤害恒 0 |
| 28 | `_loadObjectives()` 跑在 `_loadChapterLinks()` **之前** | `_chapterLinks` 空 → 拼不出 `EventListScr_Prologue_Misc` → 胜负条件表为 null → "条件命中"永远不发生 |

## 第 26 个值得单独记

`UNIT_FACTION(aUnit) = aUnit->index & 0xC0`（`include/bmunit.h:477`）——
**编号的高位就是阵营**。我方 0x01..0x3F / 友军 0x41..0x7F / 敌方 0x81..0xBF。

我早先为了修"敌人顶掉我方组件"的 id 撞车，把编号改成从 `0x100` 全局递增 ——
**修好了一个症状，引入了一个更深的**：编号落在区块外，阶段计数恒为 0。
按区块分配同时解决两件事，而且和原作一致。

## 第 27 个：位置记录解构是新的藏身处

```dart
(int avoid, int defense) terrainBonuses(...)          // 定义
final (terrainDef, terrainAvo) = _terrainBonuses(...) // 调用：反了
```

改成**具名记录** `({int avoid, int defense})` 之后，调用点必须写
`.defense` / `.avoid` —— 顺序错了**编译不过**。这是本轮唯一一个
"用类型系统把 bug 挡在门外"的改动，值得推广。

## 还有一条：**"打通了"之后画面是全黑的**

第一次跑通 `battle` 场景时，转储 13 条判据全过（章节=1、地图=Ch1Map、
单位都在），而**截图全黑**。原因是 `MNC2` 之前那次 `FADI` 留下的黑屏
**没人散** —— 原作靠章节标题卡把它淡回来
（`ChapterIntro_DrawChapterTitle` + `ChapterIntro_LoopFadeToMap`），我们没实现。

**转储看不见这件事，只有像素能证明。** 所以判据里加了一条：
中间区域的非黑像素比例 < 0.05 就红。

> 这一条是"转储 + 截图各自证明不同的东西"的又一个例子：
> 转储证明**状态**对，像素证明**画面**对。两个都要。

## 又写错一条判据

`event_skip_test` 里我断言"不快进时 `ShowText` 会阻塞"。红了 ——
但那是**判据错**：`Scene` 只负责产出事件，"等按键"在 `Fe8Game` 里。
core 测试的 `onEvent` 立即返回，脚本当然跑得完。已删掉那条，

# 附录六：接上真实移动消耗表（第 29、30 个 bug）

"把已提取但没接上的数据接上去"看起来是最安全的一类改动 —— 数据是对的，
只差一个接线。结果它**当场**暴露了两个真 bug，而且是这一整轮里
最影响可玩性的两个。

## 第 29 个：友军会把路堵死

选中单位后，我原来的规则是"光标只能走在移动范围内，**且不能停在有人
的格子上**"，两句写在同一个 `case` 里。第二句听起来无害（原作确实
不允许停在别人身上），实际效果是**光标不能经过友军格**。

序章开局：赛特 (4,4)，艾莉卡 (4,5)。(4,5) 是赛特通往东侧战场的**唯一一格**
（另外三面是山峰）—— 于是赛特一步都走不出去，整场打不起来。

原作：`src/UpdatePathArrowWithCursor.c:31-33`

```c
SetWorkingBmMap(gBmMapMovement);
if (GetBmMapPointAtCursor() == -1) return;   // 只看在不在移动范围内
```

**它只检查"在不在范围内"，友军格子照走。** "不能停在别人身上"是
**确认时**的规则。两者不是一回事，我把它们合并了。

> 教训：一个"听起来也是这么回事"的附加检查，可能把语义改掉。
> 判据要写在**每条规则各自**的层面（这条现在有独立用例）。

## 第 30 个：第 2 个敌方阶段，敌人不动

`advanceToNextActivePhase` 原来是：

```dart
switchPhases(field);
if (!shouldAutoEndPhase(field)) { beginPhase(field); return hops; }   // 清**新**阵营
```

而原作 `src/bm_08015434.c:82-95`：

```c
ClearActiveFactionGrayedStates();   // 清**当前**（即将结束的）阵营
SwitchPhases();                     // 再切阵营
```

清的是**出去的那个**。于是每个阵营的灰化都在**自己阶段结束时**被清掉，
轮到它时自然都能动。

我的版本清的是**进来的那个**，而且**只在它还有能动的人时才清** ——
后果：一个阵营只要在某次检查时全灰，就**永远**全灰。
第 1 个敌方阶段正常（单位刚载入，本来就没灰），**第 2 个回合起敌人一步都不动**。

判据（`test/core/turn_loop_test.dart`）：连续走两个回合，
断言第 2 个敌方阶段的 `phaseAbleCount(red) == 2` —— 这条曾经红过。

> 有意思的是：我自己的文档注释写着"**必须在每个阶段开始时调用**，
> 否则第二个回合起所有单位都会保持已行动" —— 症状描述得**完全正确**，
> 但把调用时机说反了，而代码照着注释写的。**注释里的因果关系也可能是错的。**

# 附录七：回合系统（第 31、32、33 个 bug）

起因是一句提问："**没有做回合吗？**"
去查才发现在"回合"这条链上，我只做了一半：阶段切换、回合计数、
灰化清空是对的，但下面三件事都没做 —— 而且**都不报错**。

## 第 31 个：`LOAD1` 不查"这个角色已经在场上"

序章的敌人被载入**两次**：开场脚本末尾一次
（`EventScr_Prologue_ONeillSpawn`），回合 1 的敌方阶段事件
`EventScr_Prologue_Turn1` 又一次（`src/data/data_08A612F4/data_08A612F4.s:32-40`）。

原作 `LoadUnit_0`（`src/eventscr_0800F8D4.c:45-95`）先按角色号找场上已有的单位，
**找到就不新建**（只改阵营 / 挪位置）。不查的后果是奥尼尔和两个杂兵各变成两份。

> ⚠️ 我按"角色在场上唯一"实现；原作的**非我方分支**只查 BLUE 区块
> （`GetUnitFromCharIdAndFaction` 只搜一个区块，`src/GetUnitFromCharIdAndFaction.c:31-42`），
> 照那条读会照样重复。**这一处与原作不完全等同，已写在代码注释里。**

## 第 32 个：事件标志被"每演完一条就清空"

`_loadObjectives()` 里有一句 `eventFlags.clear()`，而它在**每演完一条胜负条件
之后**都会被调一次。于是：

* `doneFlag`（= 原作的 `info->flag`，靠 `StartEventFromInfo` 的 `SetFlag` 记
  "这条演过了"，`src/eventinfo_080851B8.c:148`）立刻被抹掉 →
  **同一条事件无限重演**（实测 `EventScr_Prologue_OneEnemyLeft` 每回合重演）
* 刚推导出来的 `EVFLAG_DEFEAT_BOSS` 也被抹掉 → **打死首领不再触发结束脚本**

原作在**战斗地图开始**时清：`StartBattleMap` → `ResetChapterFlags()`
（`src/bmio_08030D50.c:151`）。标记必须跨事件保留 —— 这正是 `doneFlag` 的意义。

## 第 33 个：我自己刚引入的 —— 原地待机按不出来

上一节修"友军把路堵死"（第 29 个）时，我把"不能停在有人格子上"写成
`unitAt(x,y) != null` —— **把自军那一格也挡住了**。后果不是"多按一下方向键"，
而是**站在原地待机这个操作根本做不出来**（选完单位一确认就被拒）。

自己的格子是合法落点。判据写在 `flow_machine_test.dart` 里，和"友军格能穿过"
是同一条用例的两半。

## 另外两处补上的机制

* **回合事件表**（`turnBasedEvents`）：我从来没读它。
  出处 `RunPhaseSwitchEvents`（`src/RunPhaseSwitchEvents.c:38-49`）——
  一次阶段切换会把**所有命中的**按顺序演完（`SearchNextAvailableEvent` 的循环），
  只演第一条会把序章"奥尼尔攻击"教学吞掉。
  判定是 `EvCheck02_TURN`（`src/eventinfo_08085B30.c:69-88`）：
  `maxTurn == 0` 表示"只有那一回合"、`0xFF` 表示"从 turn 起无限期"。
* **自动结束阶段 / AI 行动后查等待事件**：`PlayerPhase_HandleAutoEnd`
  （`src/playerphase_0801D808.c:52`）与 `gProcScr_CpPerform` 的
  `PROC_CALL_2(RunPotentialWaitEvents)`（`src/data/data_085D1F2C/...:40`）。
  原来 `_checkObjectives` 只在 `endTurn` 开头查一次、而且是非阻塞的 ——
  **敌方阶段里打死首领什么都不会发生**（Seth 反击杀奥尼尔那条路就是这么断的）。

## 提取器的一个新坑：`CALL(指针)` 的编码

```c
#define CALL EvtCall                                    // include/EAstdlib.h:36
#define EvtCall(scr) _EvtAutoCmdLen4(EV_CMD_CALL), (EventListScr)(scr),
#define _EvtAutoCmdLen4(cmd) _EvtArg0(cmd, 4, 0, 0)     // ← arg0 恒为 0
```

**arg0 恒为 0，脚本指针在紧随的那个字里**，引擎取它用
`EVT_CMD_ARG32_BE`（`src/sub_800DC40.c:8-11`），并且"指针为负 → 从槽 2 取"。

我的解码器没有这个特例，落到兜底 `CALL(0)` → 生成器又当成"槽 0" →
**整段被调脚本静默丢掉**。修好后 `await s.call(...)` 从 402 处涨到 523 处。

> 这一条最像"数据在、但用不了"：表里明明有 `EventScr_Prologue_Turn1`，
> 它也在"已实现脚本"名单里 —— 只是**没人真的调用它**。
