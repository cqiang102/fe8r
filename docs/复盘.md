## 二、老是犯错的模式

### 把 12 个真 bug 排出来，会发现**它们是同一件事**

| # | Bug | 我当时的做法 |
|---|---|---|
| 1 | `MNC2` 是占位符 → 永远停在序章 | 没查 `EvtChangeChapterBM` |
| 2 | `LoadUnits` 只写 HUD 字符串 | 没查 `LOAD1` 该干什么 |
| 3 | `MOVE` 只写 HUD 字符串 | 没查 `EvtMoveUnit` |
| 4 | `WANTED_SCALAR = ("number",)` → 职业无属性 | 没查 `struct ClassData` 有哪些字段 |
| 5 | `number` 是枚举名 → 索引全空 | 没查 `data_items.c` 写的是什么 |
| 6 | `allegiance` 1=绿，我以为 1=红 | **想当然** |
| 7 | `LOMA` 少调 `RestartBattleMap()` | 没查 `eventscr_0800F390.c` |
| 8 | 单位 id 撞车 → 我方被顶掉 | 没想过 id 要唯一 |
| 9 | 提取器只扫三个目录 → 少 2/3 的表 | 靠**猜目录名** |
| 10 | `glob` 少 `recursive=True` | 不知道 `**` 不递归 |
| 11 | `.byte`/`.4byte` 混在一个 list | 没看两种指令的区别 |
| 12 | `_followCursor` 是我**自己发明**的 | 没查 `HandleMoveCameraWithMapCursor` |

**一句话：我写的是「看起来合理的实现」，而不是「源码里的实现」。**

### 四个更深的模式

**① 静默失败**
这 12 个 bug **没有一个报错**。全都是"跑起来了，但不对"。
最危险的是 ④⑤：战斗**悄悄退回演示数据**，界面上一切正常。

**② 用「数字对」自我安慰**
修 id 冲突那次最典型：HUD 一直显示正确的坐标，我就以为没问题 ——
**而错的是画面，不是数字**。我盯着对的那一半看了好几轮。

**③ 我自己造的工具把我骗了**
`FE8R_NODELAY` 是我为了"推长过场"加的，结果它把输入在场景开始前就丢光了，
我却据此得出「`loadMap(0)` 从未执行」的**错误结论**，还写进了提交信息。

**④ 找到"一个可疑的东西"就当成"找到了原因"**
`Event_TextWithBG` 缺失 → 我怀疑它是根因。后来验证：**不是**
（`Scene.call` 对缺脚本是优雅返回的）。
我当时写了"因果还没坐实"，但语气上已经把它当成结论了。

**⑤ 记错事实还当事实叙述**
我说了好几轮"艾莉卡在 (13,9)" —— 那其实是**赛特**。
源码一直是 `charIndex=0x02`(SETH)。**提取没错，是我叙述错了。**

### 而有效的技术，全部是**判据**

| 判据 | 抓到的东西 |
|---|---|
| **截图字节完全相同 ⇒ 改动没生效** | `Anchor.topLeft` 空操作、`FE8R_NODELAY` 假象 |
| **字节数严丝合缝** | 事件脚本解码（12 条命令 / 13 字）|
| **把两边的依据都显示出来** | 单位 id 冲突（HUD 坐标 vs 光标位置）|
| **指令轨迹（最近 N 条）** | 「场景停在第 2 条指令」|
| **分阶段截图**（停在中途） | 动作菜单其实弹出来了（是脚本时序问题）|
| **用美版 C 交叉验证日版字节** | 解码正确性；还发现美版坐标不同 |
| **测试红了是好事** | 125→406 张表、8→15 章、"没有敌军"变"有敌军" |
| **「正向判据」而非「没崩」** | `byNumber` 长度 > 200（索引没空）|

### 最后一条，也是最有效的

**用户的眼睛。** 你报了 6 次「不对」：
单位不对 / 剧情不动 / 按源码做 / 光标不对 / 我方不对 / 相机不对 ——
**每一次都指向一个真 bug，没有一个是我多虑。**

而我的第一反应常常是解释「应该是对的」。**这个顺序反了。**

## 三、怎么改：把「靠自觉」变成「靠机制」

### A. 让"没接上源码"变成 CI 失败（最高价值）

**已经被证明有效的一条**：`check_architecture.dart` 的 R7 要求
`lib/core` 每个文件有 `PORT OF:` 头 —— 它已经拦过我一次。

**要加的**：

1. **占位符棘轮**：`s.placeholder(...)` 的数量只许降不许升。
   现状 16。CI 记录数字，**变大就红**。
   （这直接对应 bug ①②③）
2. **禁止硬编码的游戏数值**：`lib/game` 里出现 `classId: 0x2A` 这类字面量就红。
   （对应 bug ④⑤）
3. **每个提取器输出后做"正向抽查"**：
   不是"文件存在"，而是"`CLASS_EIRIKA_LORD.baseDef == 3`"。
   （对应 bug ④⑤⑨）

### B. 静默失败必须响亮

1. **查表失败要抛**（debug 模式）或**写进一条必红的测试**，不是写 HUD。
2. **`_addUnits` 后断言**：单位真的落在 `field.units` 里、id 真的唯一。
   （对应 bug ⑧）
3. **`BattleView` 断言**：`_unitById.length == field.units.where(alive).length`。
   （这条会**当场**抓到 id 冲突）

### C. 判据先于实现

**规则**：动代码之前，先写下「什么可观测的东西能证明我做对了」。
提交信息里**必须**带这一行。

这次做得好的例子就是提交 `c2caaf6`（"含严丝合缝判据"）——
判据写在标题里，后来一路受用。

### D. 先搜源码，再写代码

1. **`docs/源码索引.md` 扩成「功能 → 源文件」的索引**，
   写任何玩法逻辑前先查它。
2. **没有 `PORT OF:` 就不许写** —— 把 R7 从 `lib/core` 扩到 `lib/game`。

### E. 禁止"用字符串切片改代码"

我用 `s.index(...)` + 切片删掉了 `_loadSceneData()` 和 `backgroundColor()`，
靠"编译不过"才发现。**如果删掉的是不报错的东西就会静默损坏。**
→ 一律用 `edit` 的精确替换。

### F. 事实必须带出处

**规则**：任何关于项目数据的陈述，都要能指到 `文件:行`；
指不到就标注「**未查证**」。
（对应"艾莉卡/赛特"那次）

### G. 删掉会骗人的工具

`FE8R_NODELAY` 已经没有正面价值（它制造了假象）。
**要么删，要么在名字和输出里标明"这个模式会丢输入"。**
→ 已确认：它只在"场景开始前"丢输入。**应当删掉。**

### H. 用户的观察优先

**规则**：用户说"不对" → **先当成"存在 bug"去构造判据**，
而不是先解释"应该是对的"。
这次 6 次全中，说明**用户的观察比我的自检可靠**。

---

## 四、一句话

**这 12 个 bug 里，没有一个是"算法难"，全部是"没读源码 / 没设判据"。**

所以改善的方向不是"更小心"，而是**把判据做成机器执行的**：
* 没接源码 → CI 红
* 静默失败 → 断言红
* 数字对但画面错 → **两边的依据都显示出来**

| # | Bug | 形状 |

| 13 | `MapUnit.items` 是 1 个元素的表，而 `UNIT_ITEM_COUNT = 5` | 静态结构写小 → `UnitAddItem` 永远失败 → **艾莉卡拿不到细剑** |
| 14 | `CombatResolver` 持有演示道具表，换表时没换结算器 | 对象引用 vs 变量：`_items = _realItems()` 换的是变量 |
| 15 | 提取器把 `.attributes = IA_WEAPON \| ...` 当字符串 | 枚举没解析成数 |

| 18 | `ChapterLoader.load` 自己手写 `MapUnit(...)`，漏了 `charIndex`/`items` | **同一个转换写两遍**，必然漂 |

## 三个"工具在撒谎"的新教训

**① 指标分不清自己在数什么，就会制造假 bug 报告。**
上一轮我把 `componentCount = 6`（= 5 个单位 + 1 个光标）读成"有幽灵精灵"，
**还当成一个发现报告了**。指标现在拆成
`unitComponents / markerComponents / cursorComponents`，判据只比第一项与存活单位数。

**② 一个恒为真的字段比没有字段更糟。**
`scene.running` 原来写的是 `sc != null` —— 场景对象一加载就非空，
这个字段**永远是 true**，看起来像"场景在跑"，实际什么都没说。
现在它读的是真的 `_sceneRunning`。

**③ 转储自己也会静默失败。**
`slots` 的键写成了 int，`jsonEncode` 编不了 —— 而**只有槽非空时才炸**：
标题画面那会儿转储正常，一到序章（脚本真的用了槽）整个转储失败。
要命的是 `scenario.sh`/`shot.sh` 的输出被 `grep` 过滤过，
`[dump] 失败` 那行看不见，我只能靠"文件不在"猜到。
现在：**转储缺失 = 失败**，报错行会打出来。
（这类"跑 60 秒才知道"的事，现在有一条 1 毫秒的测试：
`dumpState()` 必须可 JSON 编码，且槽非空。）

## 这一轮做成的机制（都带证伪）

| 机制 | 判据 | 证伪方式 |
|---|---|---|
| **占位符棘轮** | `placeholder` 调用点 / op 名 / 缺失脚本，任一变大即红 | 往生成物里加 2 个占位 → 红（3757→3759）；`--selftest` 也验 |
| **转储判据**（14 条）| id 唯一 / 渲染数==存活数 / 5 槽 / 坐标 / 相机 / 细剑 / 名册 / 场景跑完 | `--selftest` 喂 6 个**故意坏掉**的转储，要求每条都被抓到 |
| **端到端场景** | `scenario.sh prologue` → 真机转储 → 判据 | 放进 `--e2e`（默认不跑，**默认的"通过 N 项"不含它**）|
| **`loadRuleData()` 拆出来** | 规则层数据可单测 | 原来整条 `onLoad` 在 widget test 里**走不完**（图片解码），bug 只能靠肉眼 |

## 还有一条：**提交信息里的数字也是断言**

我写完提交信息后去核对门禁输出，发现自己写的「41 项」实际是 **40 项**（41 是
带 `--e2e` 的数）。已经改掉重提交。
**凡是我写下的数字，都要来自刚跑过的输出，不能来自"应该差不多"。**

## 三处用户报告的根因（一句话）

```
开场链路  →  tick() 接在按键上（时间是帧驱动的）
序章剧情  →  道具栏 1 个元素（UnitAddItem 永远失败）→ 艾莉卡没武器
序章战斗  →  结算器持有演示道具表（细剑 9 号查不到 → 威力 0）
```

**都不是"算法难"，全部是"没读源码 / 没设判据"。** 和第 1–12 个一模一样。

## 最该记住的一条：**我"核对过"的结论本身可能有错**

上一轮我写过：

> ```
> LOMA(0x10) → 章节 16 (E15) → Ch16Map          ← 王座厅（王宫内）
> LOMA(0x40) → 章节 64 (0x40) → GradoCastleMap  ← 王宫外
> ```
> **三张图、三段剧情 —— 与用户描述一字不差。**

第二行是**错的**。它是用"名字键"查的表：`CH64` 这个**符号**在数组里是
第 **63** 项，而 `LOMA(0x40)` 要的是第 **64** 项（`CH65` → `RenaisCastleMap`）。

**我当时的"核对"是拿一张和自己不一致的表去对** —— 症状（地图没换）一直都在，
只是我把两处错误互相抵消着看过去了。

还有一条同类：`docs/images/ch1-map.png` 的 HUD 上写着 **`PrologueMap`**，
而它被当成"第一章地图加载了"的证据留了下来。

**教训：一张图里的文字，比我对这张图的描述可信。核对结论时，先把图/数据里
写的东西读出来，再下判断。**
