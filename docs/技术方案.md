## 0. 一页速览

### 0.1 核心判断

**可行。而且"全流程 AI 驱动"这个要求，恰好和这个项目的本质高度契合。**

原因是一个容易被忽略的事实：**这个项目是"翻译"，不是"创作"。**

| 要做的事 | 参照物 | 是否存在唯一正确答案 |
|---|---|---|
**但要先分清一件事：这个项目里只有一部分是"翻译"，另一部分是"设计"。**

| 要做的事 | 参照物 | 性质 |
|---|---|---|
| 移植战斗公式 | `src/GetUnitDefense.c` 等规则层源码 | ✅ **翻译**（有唯一正确答案） |
| 移植 AI 决策 | `src/Ai*` 系列 | ✅ **翻译** |
| 导出数据表 | `data_characters.c` / `data_classes.c` / ... | ✅ **翻译** |
| 解析地图 | 66 个 `.mar` + 66 个 `.json` | ✅ **翻译** |
| 解析事件脚本 | `src/data/EventScr_*_ref/` 的可读 EA 宏 | ✅ **翻译** |
| 翻译文本 | `texts/jp_texts.txt` 的 3339 条明文 | ✅ **翻译** |
| 播放音乐 | 588 个原始 MIDI + 439 个 AIFF 采样 | ✅ **翻译** |
| 重绘美术 | 2960 个 JP 原版 PNG | ✅ 有原图（结构可机器校验 + 多模态视觉判定） |
| **重写菜单 / UI** | 原版只是**参考**，不是标准答案 | 🎨 **设计** |
| **重写特效 / 转场 / 战斗动画播放** | 原版只提供**时序数据** | 🎨 **设计** |
| **重写输入 / 存档 / 设置** | 原版是 GBA 约束的产物 | 🎨 **设计** |

**⭐ 核心原则（贯穿全方案）：**

> **GBA 代码里的"怎么做"不值得保留，"做什么"必须保留。**

这让工作量大幅下降——见 §2.6 的实测拆分：**只有约 13–17% 的代码需要严格移植，约 35% 是表现层重写（设计而非翻译），约 8% 直接消失。**

所以四条核心判断是：

1. **数据不是瓶颈，是最大的红利。** `fireemblem8j` 已经把整个游戏"打开"了——数据表是类型化 C、事件脚本是可读宏、文本是明文、地图是 `.mar`+`.json`、音乐是原始 MIDI。而且它的**源代码本身就能构建出字节一致的 ROM**（见 §2.2），这意味着连"标准答案机"都不需要用户提供 ROM。
2. **"零人工"是可以工程化的，而且已经过了实测。** 方案的核心是五层验证体系（§6）。其中两层已在本机跑通：
   - **C Oracle**：在 macOS 上用 host clang 编译真实的编译产线 C 代码作为判卷标准。**实测 6175/6213 = 99.39% 的源文件可直接编译，不需要 ROM、不需要 arm 工具链、不需要修改上游任何文件。** RNG 与 `GetUnitDefense` 的运行时交叉验证已逐位通过。
   - **字节级往返验证**：`源码 → 我们的内部格式 → 重新序列化 → 与原文件逐字节比对`。已实测 `.mar` 地图**无损**（26541 个瓦片值全部可逆）。因为反编译项目的 CI 已证明 `源码 ⟶ ROM` 字节一致，所以往返一致就**传递性地**证明了与原版 ROM 一致——**全程不碰 ROM**。
3. **Flutter 让 GBA 的架构包袱整体作废。** 1301 个文件引用 GBA 手写的 Proc 协程系统、311 个文件手动管理 OAM/VRAM、282 个文件手写文本绘制、598 个文件在做调色板过渡特效——**这些在 Flutter 里全部被原语替代**（`async`/动画控制器、`SpriteComponent`、`Text`、shader）。GBA 上超过一半的代码存在的原因是硬件限制（96KB VRAM、无操作系统、无文件系统、单线程），Flutter 没有这些限制。**不移植清单见 §4.8。**
4. **唯一无法完全自动化的是审美判断**，而这个可以降级、可以延后（见 §1.4）。工程正确性可以 100% 自动化；"好不好看"需要人，但它不阻塞任何功能。

## 1. 目标与范围

### 1.1 项目定位

不是"用 Flutter 写一个战棋游戏"，而是**把 FE8 的游戏逻辑原样搬进 Dart，替换掉它的表现层**。

这个定位决定了几乎所有架构选择：

- 游戏规则、数值、AI、事件流程 → **严格照搬**，不做"我觉得这样更好"的改动
- 渲染、UI、美术、交互 → **完全重做**，不受 GBA 240×160 的物理限制
- 两者的边界必须极其清晰，否则改一个 UI 细节会意外改变战斗结算

**为什么这个定位对 AI 驱动至关重要**：如果允许"自由发挥"，AI 的每次产出都需要人判断"这样对不对"。而"照搬"意味着存在一个可程序化比对的标准答案，AI 可以自己判断自己对不对——**闭环自动化才有可能**。

### 1.2 范围

**In Scope**

| 系统 | 说明 |
|---|---|
| 地图与网格 | 66 张章节地图、地形推导、地图变更（开宝箱/破墙/增援） |
| 单位系统 | 角色/职业/道具/武器等级/状态异常/救援/三角攻击 |
| 战斗结算 | 伤害/命中/必杀/连击/特效武器/武器三角/地形加成 |
| 战斗动画 | 201 套 banim 动画（图集 + OAM 脚本驱动） |
| 成长与转职 | 升级乱数、成长率、转职分支、职业上限 |
| 支援系统 | 支援对话、支援等级加成 |
| 敌方 AI | 复刻 `AiAttempt*` 系列决策 |
| 事件引擎 | 70+ opcode 解释器、剧情演出、增援、胜利条件 |
| 回合流程 | 玩家/敌方/友方/同盟回合、目标判定、评价 |
| 章节流程 | 世界地图、章节选择、准备画面、运输队/商店/竞技场 |
| 存档 | 随时存档、多存档位、中断存档 |
| 文本 | 3339 条消息中文化 |
| 表现层 | 宽屏 UI、高分辨率美术、AI 重绘素材 |

**Out of Scope（明确不做）**

- 通信斗技场 / 联机（GBA link cable 功能）
- 原版 ROM 的字节级重建（那是 decomp 项目的目标，不是我们的）
- 模拟器方案（在 Flutter 里跑 GBA ROM）—— 技术上不可行且法律风险最高，已排除

### 1.3 保真度契约

需要明确区分两类改动：

**A 类 — 必须逐位一致（Numbers Contract）**

> 给定相同的初始状态与相同的乱数序列，任何战斗结果、成长结果、AI 决策**必须与原版完全相同**。

覆盖：伤害公式、命中/必杀公式、武器三角、特效、地形加成、升级成长、支援加成、AI 目标选择与站位、**乱数消耗顺序**。

**B 类 — 允许现代化（UX Contract）**

| 改动 | 说明 |
|---|---|
| 战斗动画加速 / 可跳过 | 保留原演出，增加 2×/4×/跳过 |
| 随时存档 + 多存档位 | 原版仅中断存档与章节存档 |
| 难度选项 | 保留原始三档，额外提供"现代模式" |
| 高分辨率 + 宽屏布局 | 完全重做 UI 布局，不受 240×160 限制 |
| 鼠标 + 键盘操作 | 桌面原生交互（hover 预览、右键取消、快捷键） |

**关键约束**：B 类改动**不得**改变 A 类的输入输出。例如"战斗动画加速"只改播放速率，不能改乱数消耗次数——原版中每个动画帧是否消耗乱数是确定的。

### 1.4 ⭐ "尽量不人工"的可行性边界

这个要求必须被诚实地拆解，否则会在中期变成"AI 写了一堆没人能验收的代码"。

**能 100% 自动化判定的（占工作量的绝大多数）**

| 工作类型 | 判定手段 |
|---|---|
| 数据表导出 | 导出条数 vs C 源码条数；抽样值比对；schema 校验 |
| 公式/算法移植 | **C Oracle 批量对照**（§6.4） |
| 事件流程移植 | 事件脚本回放 + **状态哈希比对**（§6.3） |
| 地图解析 | 瓦片网格校验和 与 ROM 内的地图数据比对 |
| 渲染正确性 | **结构断言 + 参考渲染器 diff**（§6.5） |
| 回合流程 | 事件状态机回放 + 存档往返（§6.4.2） |
| 音频渲染 | 频谱/时长校验 + 人工抽听（可选） |
| 资源结构变换（2× 放大等） | 尺寸/网格对齐/调色板数量断言 |
| 文本翻译的硬伤 | 双向回译自检 + 术语表一致性 + 控制码完整性 + 长度约束 |

**无法完全自动化、需要人（但可降级、可延后）**

| 工作类型 | 为什么难 | 对策 |
|---|---|---|
| **美术审美质量** | "好不好看"没有客观函数 | 把"结构正确"和"审美合格"**拆开**。结构正确可自动验证（尺寸、网格、调色板、图层），先保证结构正确——游戏就能跑。审美放到最后，人工挑图 + 重跑 |
| **翻译语感** | 细腻的语气、双关、角色口癖 | 硬伤可自动查（回译、术语、长度）；语感由人工在最后统一润色一遍。**不阻塞功能** |
| **架构决策** | 需要判断力 | 借鉴 decomp 项目的做法：AI 自主决策 + 写进决策日志 + 用"硬不变量"兜底（§7.7）。偏离了不变量会立刻红灯 |
| **宽屏布局设计** | 需要设计判断 | 以原版截图为 golden 基准做像素 diff 驱动；宽屏扩展部分用规则化布局算法，只在最后做人工微调 |

**⭐ 加上 §4.8 的分层之后，这张表要重新解读：**

| 层 | 能否自动判定 | 说明 |
|---|---|---|
| **规则层**（~820–1050 函数，占移植工作量 100%） | ✅ **能** | 有唯一正确答案，C Oracle 逐位对照 |
| **数据层**（表 / 地图 / 文本 / 事件脚本） | ✅ **能** | 有唯一正确答案，字节级往返 |
| **表现层**（~2151 文件的工作量） | ⚠️ **部分能** | 结构可断言；**设计与美感不能** |
| 平台层 | — | 不存在，无需判定 |

**这带来一个重要的重新定位：**

> v2.0 里"AI 全自动"的论证建立在"这是翻译不是创作"之上。**但加上 §4.8 之后，事实是：约 2/3 的工作量是"设计"（表现层重写），只有约 1/3 是"翻译"。**

所以诚实的结论是：

- ✅ **规则层 + 数据层可以做到接近 100% 的 AI 驱动 + 机器判定**——这是项目的"骨干"，也是"重置版不是另一个游戏"的保证
- ⚠️ **表现层的实现可以由 AI 完成，但"设计决策"（布局怎么排、动画多快、特效多强）需要人或明确的规范**
- 🎯 **对策**：给表现层任务提供**足够具体的规范输入**，把它从"设计"降级为"实现"：
  - 布局 → 以原版截图为参照 + 明确的宽屏扩展规则
  - 动画时序 → 从原版数据里提取（`ProcScr` 的 timer 值，见 §4.8.3）
  - 特效 → 从原版函数名与参数提取视觉意图
  - 视觉风格 → 已定的 D 混合风格（§5.3）

**这样表现层任务就变成"有参照的实现"而不是"自由创作"，机器判定的覆盖率大幅提升。**

**最终结论**：`AI 生成 + AI 测试` 在**规则层与数据层**上可以做到接近 100% 自动化；在**表现层**上可以做到"有规范约束的实现"，自动化程度取决于规范给得多细。**审美质量**不能自动化，但可以降级、可以延后，不阻塞功能。

### 1.5 完成标准（Definition of Done）

| 级别 | 定义 |
|---|---|
| **DoD-1 技术验证** | 序章可完整通关：地图渲染正确、单位移动范围正确、战斗结算与原版一致、剧情事件播放完整、可存档。**且所有验证层绿灯** |

**三个"意外之喜"，直接砍掉了原本最难的几块工作：**

1. **文本已经是明文。** `texts/jp_texts.txt` 是反编译项目 dump 好的、可直接阅读的日文（`#0xNNNN` 分隔），**不需要**自己解 Huffman 压缩：

   ```
   顔ビューア
   ```

2. **事件脚本已经是可读宏。** 我最初从 `_ref` 这个命名判断它是不透明二进制，实际拉取后是 **EA（Event Assembler）宏形式**：

   ```c
   SECTION(".rodata.dat_EventScr_Ch10A_0_ref") EventListScr EventScr_Ch10A_0[] = {
       CAMERA_CAHR(0x4F)
       CURSOR_CHAR(0x4F)
       STAL(0x3C)
       CURE
       MUSC(0x14)
       TEXTSTART
       TEXTSHOW(0x9F1)
       TEXTEND
       REMA
       SVAL(EVT_SLOT_2, 0x13)
       CALL(Event_TextWithBG)
       EVBIT_T(7)
       ENDA
   };
   ```

   这砍掉了"先写事件脚本反汇编器"这一整块工作——事件引擎只需要解析宏调用序列。

3. **音乐是原始 MIDI。** `sound/songs/midi/` 下 588 个 `.mid`（已验证 `song001_agbfe3_bgm_opening.mid` 存在），不是从 GBA 的 m4a 字节码反向还原的。

### 2.2 ⭐ 为什么反编译的 C 源码是绝对权威

这是整个验证策略的地基，值得单独说明。

**我们不需要自己构建 ROM。** 反编译项目的 CI 已经持续证明了「源码 ⟶ ROM」字节一致；我们只要证明「源码 ⟶ 我们的内部格式」忠实，就能**传递性地**继承那个证明（见 §6.2）。下面这些事实是那个证明的依据。

`fireemblem8j` 的构建是**完全自包含**的：README 与 CI 都明确声明 `baserom.gba` **不是构建输入**，`make compare` 会从已提交的源码构建出 `fireemblem8.gba`，然后用 `sha1sum -c checksum.sha1` 验证它与原版 JP ROM 字节一致。

CI 在干净的 ubuntu runner 上的完整依赖（`.github/workflows/ci.yml`）：

```
系统包：  build-essential  binutils-arm-none-eabi  libpng-dev  bash
Python：  ttp  requests  numpy  Pillow
工具链：  agbcc（scripts/build_jp_agbcc.sh，带 -mjp-promote 补丁）
          gbagfx / bin2c / preproc / aif2pcm / mid2agb / scaninc
          （从 fireemblem8u 克隆后本地构建）
子模块：  mgfembp（FE6 SIO 多机通信载荷，自带 agbcc 构建）
验证：    make compare → "fireemblem8.gba: OK"
```

**这意味着**：

- ✅ 反编译的 C 源码、数据表、资源文件都是**经过字节级验证**的，可以直接当作判卷标准
- ✅ 我们**既不需要 ROM 文件，也不需要构建 ROM**——那套工具链（`arm-none-eabi` + agbcc + 6 个资源工具 + 子模块）与本项目目标无关，已决策移除（D13）
- ✅ 传递性证明的链路：`反编译 CI 证明 源码 ≡ ROM` 且 `我们的往返验证证明 内部格式 ≡ 源码` ⟹ `内部格式 ≡ ROM`

> 附带验证：macOS 上 `iconv` 的 CP932 转换正常（输出与 glibc 一致），实测通过。这是当初怀疑的一个 macOS 风险点。

### 2.6 ⭐ 工作量实测拆分：GBA 的架构包袱占多少

`src/` 顶层有 **6213 个 `.c` 文件**。但**它们不是同一种东西**。

核心判断原则（贯穿全方案）：

> **GBA 代码里的"怎么做"不值得保留，"做什么"必须保留。**

- 屏幕闪白：**做什么** = 闪白 160ms 再闪回。**怎么做**（改调色板 / `CpuFastCopy` / `Proc` timer）全部丢弃。
- 战斗伤害：**做什么**和**怎么做**都保留——公式就是规则本身。

按这条线对全部 6213 个文件做特征分类（实测）：

| 层 | 特征 | 文件数 | 处理方式 |
|---|---|---:|---|
| **平台层** | 硬件寄存器 / OAM / VRAM / DMA / SRAM 时序 / m4a 音频引擎 | **485** | ❌ **不再存在**。Flutter 直接替代 |
| **表现层** | Proc 协程 / 菜单 UI 框架 / 文本绘制 / 特效与调色板过渡 | **2151** | 🔄 **用 Flutter 原语重新实现**，不移植 |
| **规则层** | 战斗公式 / AI / 地图寻路 / 单位道具 / 事件语义 | **1051** | ✅ **必须 1:1 移植**（C Oracle 覆盖的正是这层） |
| 未分类 | 见下 | 2911 | M1 归类 |

单类特征命中数（会重叠）：

| 特征 | 文件数 |
|---|---:|
| Proc 协程（`ProcScr_` / `Proc_Start` / `PROC_REPEAT`） | **1301** |
| 特效与调色板过渡（`Efx` / `ColorFade` / `PaletteFade` / `Mosaic`） | 598 |
| 单位 / 道具（`GetUnit*` / `GetItem*` / `gItemData` / `gClassData`） | 577 |
| 菜单 / UI 框架（`MenuProc` / `StartMenu` / `HelpBox`） | 341 |
| OAM / VRAM / 精灵表 | 311 |
| 地图 / 寻路（`MapFlood` / `BmMap` / `GetMovementCost`） | 299 |
| 文本绘制（`Text_` / `DrawGlyph` / `TextPrinter`） | 282 |
| AI（`Ai*` / `AiAttempt`） | 186 |
| 事件引擎（`EventEngine` / `CallEvent` / `EventListScr`） | 185 |
| 硬件寄存器 / DMA / 中断 | 89 |
| SRAM / 存档硬件 | 76 |
| 战斗结算（`BattleGenerate` / `ComputeBattle`） | 49 |
| 音频引擎（`MPlayStart` / `SoundInit` 等） | 22 |

**关键结论：**

1. **最纯粹的移植候选只有 820 个文件（13.2%）**——即命中规则层特征、且不含任何平台/表现层特征的那些。
2. **含重叠的规则层是 1051 个（16.9%）**。这部分是"游戏"本身：公式、AI、关卡数据语义。
3. **表现层 2151 个文件（34.6%）不移植**，改用 Flutter/Flame 原语重写。**它不是"翻译"，是"设计"**——代码量通常比原版更少。
4. **平台层 485 个文件直接消失**。
5. 未分类的 2911 个是混合体（音频引擎函数、文本/UI 辅助、子系统残留），**其中 560 个（19%）还只有地址名**（`sub_803A2E8`），语义尚未还原。

**对排期的意义（与 v2.0 的关键差异）：**

| | v2.0 估算 | **v2.1 估算** |
|---|---|---|
| 移植工作量 | ~1900 个文件逐函数移植 | **~820–1050 个规则层函数** |
| 表现层 | 部分当作"移植" | **重新实现**（是新设计工作，不是翻译） |
| 平台层 | 部分当作"豁免" | **完全不存在** |
| Dart 代码量 | 接近 1:1 于 C | 粗估 **少 5–10 倍** |

> ⚠️ **分类是启发式的**（基于符号特征），精确清单需要 M1 的一次系统归类。但它给出的形状是可靠的：**只有约 1/8 到 1/6 的代码需要严格移植。**

> ⚠️ 特别注意：**1301 个文件引用 Proc 协程系统，但其中绝大多数是表现层**。AI 智能体如果被派去"移植 ProcScr"，会浪费巨量时间在注定要被丢弃的代码上。这正是 §4.8 的**不移植清单**必须存在的原因。

**每层的工作性质完全不同，必须区别对待：**

| 层 | 工作性质 | 验证方式 | 参照物 |
|---|---|---|---|
| 表现层 | **设计**——没有唯一正确答案 | 结构断言 + 视觉判定 + 与参考渲染器 diff | 原版只是参考 |
| 规则层 | **翻译**——有唯一正确答案 | **C Oracle 逐位对照** + 单元测试 | C 源码即规范 |
| 数据层 | **提取**——有唯一正确答案 | **字节级往返验证** | 原文件即规范 |
| 平台层 | — | — | 不存在 |

> **这个区分极其重要**：如果 AI 智能体把表现层也当成"翻译"来做，它会去阅读并重写 1301 个 Proc 文件、311 个 OAM 文件，产出大量注定被丢弃的代码。**§4.8 的不移植清单就是防止这件事的。**

**核心原则：数据单向流动。** `third_party/fireemblem8j` 是只读上游，`tools/` 是唯一转换者，`assets/` 是产物，`core/` 只消费 `assets/`。任何时候都不要在 `lib/` 里出现对 `third_party/` 的路径引用。

### 4.2 为什么 `core/` 必须纯 Dart 且完全可序列化

这一条值得单独论证，因为它是很多同类项目翻车的地方。

**纯 Dart（无 Flutter 依赖）**

- 8692 个函数的行为验证需要在 CI 里批量跑，没有 GUI 才能自动化
- `dart test` 比 `flutter test` 快一个数量级，而这个项目的测试量会非常大
- 逻辑层不依赖渲染，意味着可以写一个**纯文本的调试客户端**：在终端里打印地图网格、执行战斗、验证结果。这在开发早期极其有用，而且**对 AI 智能体非常友好**——AI 可以直接读文本状态来判断自己做的事对不对

**完全可序列化**

"随时存档"看起来是个小功能，实际是**架构级约束**。最直接的冲突是事件引擎：

```dart
// ❌ 诱人但错误：用 async/await 写事件引擎
Future<void> runEvent(EventScript script) async {
  for (final op in script.ops) {
    switch (op) {
      case TextShow(:final id):
        await _textRenderer.show(id);   // 玩家在这里存档怎么办？
      case Stall(:final frames):
        await _waitFrames(frames);      // 这个 await 无法序列化
    }
  }
}
```

Dart 的 `async/await` 状态藏在 VM 的堆里，无法序列化。玩家在对话播放到一半时存档，读档后事件就断了。

**正确做法**：事件引擎是一个**显式状态机**，所有中间状态都是数据。

```dart
class EventEngine {
  int programCounter;              // 当前 opcode 下标
  Map<int, int> slots;             // EVT_SLOT_0..N
  int stallTimer;                  // 等待帧计数
  EventEngineState state;          // RUNNING / WAITING_TEXT / WAITING_ANIM / DONE
  List<EventEngineSnapshot> callStack;  // CALL / ENQUEUE_CALL 的返回栈
}
```

渲染层每帧调用 `engine.tick()`，引擎根据状态推进。存读档只是对这个对象做 JSON 序列化。

**同一原则贯穿全项目**：战斗动画、单位移动动画、AI 决策过程，全部是"数据 + tick"模型，不是 `async` 函数。

> **额外收益（对 AI 驱动很重要）**：显式状态机意味着任意时刻的游戏状态都是一个可打印的纯数据对象。AI 可以 dump 它、比对它、断言它。`async` 版本做不到这一点。

### 4.3 ⭐ 语义形式原则

这是美术与资源管线最重要的一条设计原则，值得单独提出：

> **在管线里把 GBA 的表现形式还原成语义形式，引擎只消费语义形式。**

原版资源是为 240×160、96KB VRAM、索引调色板设计的，带有大量硬件约束产物。如果把这些约束带进新引擎，会同时污染架构和美术工作流。

| GBA 形式 | 语义形式 | 管线负责 |
|---|---|---|
| 立绘 = 瓦片集 PNG + TSA + 嘴部帧 + 调色板 | **一张完整的人像图 + 表情变体** | 按 TSA 拼合瓦片 → 合成完整图像 |
| 战斗动画 = 图集 + OAM 条目流 + 调色板 | **一个动画剪辑：命名部件 + 关键帧变换** | 解析 OAM 流 → 结构化的帧/部件模型 |
| 地图 = u16 瓦片索引 + metatile 定义 + 瓦片集 | **一张地形图 + 瓦片集图集 + 地形网格** | 解析 metatile → 直接合成可渲染的图层 |
| 文本 = CP932 + 控制码 + Huffman | **结构化 token 序列** | 解码 + token 化 |
| 音乐 = MIDI + voicegroup 宏 + AIFF | **OGG 音频** | SoundFont 构建 + 离线渲染 |

**收益**：

1. **引擎简单**：不需要实现 GBA 的瓦片/调色板机制，Flutter/Flame 直接用 RGBA 纹理
2. **AI 重绘变简单**：对着一张完整立绘做图像生成，远比对着一个瓦片集做要容易得多
3. **结构可机器校验**：语义形式的约束更少、更明确（尺寸、图层数、帧数），容易写断言
4. **解耦**：GBA 格式的复杂性被限制在 `tools/pipeline/extract/` 里，改错了不会影响运行时

**代价**：提取阶段必须"真正理解"每种 GBA 格式。这是 M1/M2 的主要工作量，但只做一次。

### 4.6 渲染架构

> **地图部分有独立的详细方案，见 §4.9**（Tiled 导出 / 预合成纹理 / shader 表现升级 / 红线）。本节只讲通用的宽屏策略。

**宽屏 + 高分辨率的处理策略**

原版是 240×160 的 GBA 视野，一张 15×10 的序章地图刚好铺满。宽屏下：

| 方案 | 说明 | 评价 |
|---|---|---|
| **A（推荐）动态视野** | 相机视野随窗口尺寸变化，地图外围可见部分始终填满屏幕；UI 吸附到屏幕边缘（不是地图边缘） | 保留 GBA 的"网格感"，同时利用宽屏 |
| B 固定 16:9 视野 + 黑边 | 最保守 | 浪费屏幕 |
| C 放大倍率自适应 | 窗口越大，像素越大 | 大屏上显得粗糙 |

**地图渲染层结构**（对应 FE8 的 BG 层）：

```
World
├── TerrainLayer        静态地形瓦片（管线阶段已合成为整张图层）
├── MapChangeLayer      地图变更覆盖（宝箱打开、墙壁破坏）
├── OverlayLayer        移动范围 / 攻击范围高亮
├── UnitLayer           单位精灵（gmapunit）
├── EffectLayer         特效、天气、瓦片动画
└── CursorLayer         光标
```

**关键实现点：**

- **网格与渲染解耦**：`core/map/` 只提供 `terrainAt(x, y)` 等逻辑查询；`game/components/` 把它画出来。绝不让渲染层参与地形推导。
- **调色板换色用 Shader 实现**：原版通过切换调色板实现阵营色（蓝/红/绿）和立绘表情。走 shader 后对 AI 重绘的输出格式零约束（见 §5.3.2）。
- **瓦片动画**：`graphics/mapanim/` 有 415 个帧（水面、火把），纯表现层，与游戏逻辑无关。

### 4.8 ⭐⭐ 不移植清单（负向清单）

**这是全文档对 AI 驱动开发最重要的一个清单。**

反编译项目有 8692 个函数。如果任务派发时只说"移植 FE8"，AI 会平均地对待它们，把大量时间花在注定要被丢弃的 GBA 平台代码上。**必须显式地告诉它"哪些不要碰"。**

#### 4.8.1 整体不移植（整类丢弃）

| # | 不移植的东西 | 规模 | 为什么 | 替代 |
|---|---|---:|---|---|
| **N1** | **Proc 协程系统**（`ProcScr_*`、`Proc_Start`、`PROC_REPEAT`、`PROC_END`） | **1301 个文件引用**，806 个 `ProcScr` 定义 | GBA 没有操作系统与线程，这是手写的协作式多任务 | 表现层用 `async`/`await` + `AnimationController`；流程层用可序列化显式状态机（§4.2） |
| **N2** | **菜单 / UI 框架**（`MenuProc`、`MenuItemProc`、`StartMenu`、`HelpBox`） | 341 | 手绘菜单项、光标、翻页、边框贴图 | Flutter Widgets（用户已要求重做 UI） |
| **N3** | **文本绘制**（`Text_`、`DrawGlyph`、`TextPrinter`、`gTextFont`） | 282 | Huffman 解码 + 点阵字 + 手写换行 + 写 VRAM | `Text` widget + `TextPainter` + TTF（§5.4.3） |
| **N4** | **OAM / VRAM / 精灵表管理**（`PutOam`、`gOamData`、`gVram`、`APProc`、`Tsa_`） | 311 | 手动分配 OAM 条目、VRAM 瓦片、affine 矩阵、调色板 bank | `SpriteComponent(texture, srcRect, position)` |
| **N5** | **特效与调色板过渡**（`Efx*`、`ColorFade`、`PaletteFade`、`Mosaic`、`gPaletteBuffer`） | 598 | 逐帧改硬件调色板实现闪白/闪黑/淡入淡出 | `Opacity` / `ColorFiltered` / fragment shader / 动画曲线 |

| **N7** | **SRAM / 存档硬件时序**（`ReadSramFast`、`VerifySramFast`、`gSram`） | 76 | GBA 的 SRAM 访问时序与校验和 | JSON + 文件系统 |

#### 4.8.2 规则层里的"局部不移植"

有些文件同时含规则层与平台层代码。这时**只移植规则部分**：

| 情况 | 做法 |
|---|---|
| 函数签名带 `struct Proc*` 参数但逻辑是纯规则 | 移植逻辑，`Proc` 参数改为显式状态对象 |
| 函数里读 `gBmMapTerrain` 等全局 | 移植（这些是**游戏状态**不是硬件），但改为显式传入依赖 |
| 函数里写 `*(u16*)PLTT` 之类的硬件地址 | 丢弃该部分，改为返回"要显示什么" |
| 函数里调 `PlaySoundEffect(id)` | 移植调用意图（返回音效 ID），播放交给表现层 |
| 函数里 `#if NONMATCHING` 分支 | 忽略（那是为了字节匹配，与行为无关） |

#### 4.8.3 需要"读但不移植"的（参考资料）

这些**不产生 Dart 代码**，但移植时需要读它们来理解行为：

| 用途 | 读什么 |
|---|---|
| 理解战斗公式的调用时机 | `BattleGenerateReal.c` 等（了解顺序，不逐行搬） |
| 理解菜单的**信息结构**（有哪些项、什么条件可见） | `MenuProc` 相关文件 —— **信息结构要保留，绘制方式丢弃** |
| 理解动画的**时序参数** | `ProcScr_*` 里的 timer/terminator 值 —— 用作新动画的时长参数 |
| 理解特效的**视觉意图** | `Efx*` 函数名与参数 —— 用作新特效的设计输入 |

> **一句话**：**表现层的"信息结构与时序参数"要提取，实现方式要丢弃。**

#### 4.8.4 派发任务时的强制要求

每个移植任务的配方（§7.5）**必须显式写明**：

```markdown
## 配方: src/SomeFunction.c
**范围**: 规则层 ✅
**不需要移植**: 该文件里的 ProcScr_xxx（见 §4.8 N1）、绘制到 VRAM 的部分（N4）
**提取但不移植**: timer 值 60 / 240（用作新动画时长）
```

**如果任务的 C 源文件命中 N1–N10 中任何一类，默认不派发，除非配方里明确解释了为什么需要。**

### 4.9 ⭐ 地图技术方案（现代化收益最大的地方）

地图是"GBA 约束 vs 现代技术"差距最大的地方，也是**唯一能同时降低工作量、提升效果、还白送工具链**的模块。

#### 4.9.1 出发点：GBA 的地图数据是为省钱设计的

原版地图数据里的每一个"奇怪设计"都对应一条硬件约束：

| GBA 的约束 | 数据里留下的痕迹 |
|---|---|
| VRAM 只有 96KB | 瓦片集必须复用 → `ObjectType4.png` 是 **`8×7344` 的单列瓦片条**（918 个 8×8 瓦片竖着堆） |
| 硬件只认 8×8 瓦片 | 地图用 metatile（2×2 瓦片）拼 → `TileConfiguration*.S` 每张 **1024 个 metatile**，每个 = TL/TR/BL/BR 四角 |
| 调色板只有 16 个 bank | `MapPalette1..19` 分开存放，换场景靠换 bank |
| 240×160 视野 | 地图边缘永远在屏幕外，不需要考虑全图呈现 |
| 无浮点、无 shader | 所有效果只能靠"改调色板 / 换瓦片 / 滚动 BG"实现 |

**但实际体量小得可怜**（实测）：

| | 值 |
|---|---|
| 地图总数 | 66 |
| 最大地图 | **30 × 31 = 899 格**（`Ch14EphraimMap`） |
| 最小地图 | 2 × 2（`LordsSplitMap`） |
| 全部地图合计 | **26541 格** |
| 最大地图 4× 放大后的纹理 | 1920 × 1984 RGBA ≈ **15 MB** |

**对桌面 GPU 而言这些数字完全不值一提。** 所以 GBA 的那些约束带来的复杂度，**在重制版里没有任何存在理由**。

#### 4.9.2 表示层：导出成 Tiled，白送一个关卡编辑器

**问题：地图数据现在散在五个地方。**

| 数据 | 当前位置 |
|---|---|
| 视觉瓦片网格 | `graphics/map/layout/*.mar` |
| 瓦片集与调色板 | `graphics/map/ObjectType*.png` + `MapPalette*.pal` |
| metatile 定义 | `graphics/map/TileConfiguration*.S` |
| 地形类型 | metatile → `TERRAIN_*` 的二级推导 |
| 生成点 / 单位配置 | `src/data/UnitDef_Ch*_ref/` |
| 触发器 / 增援 / 胜利条件 | `src/data/EventScr_*_ref/` |
| 地图变更（开箱、破墙） | `src/data/*MapChanges_ref/` |

**现代关卡格式把它们统一成一个文件：**

```
Tiled .tmx
├── 瓦片图层
│   ├── 地形（视觉瓦片）
│   ├── 地图变更覆盖
│   └── 装饰
├── 对象层
│   ├── 单位生成点（含阵营/职业/等级/道具）
│   ├── 宝箱 / 村庄 / 商店
│   ├── 增援触发点
│   └── 胜利条件区域
└── 自定义属性
    └── 每格的地形类型（逻辑层与视觉层在同一文件里对齐）
```

**收益：**

1. **白送一个成熟的关卡编辑器**（Tiled 免费、跨平台、跨 15 年验证）
2. 地图从"GBA 数据的副产品"变成**一等公民的可编辑资源**
3. **直接解决了 §1.4 里标记为"需要人"的宽屏布局问题**——调布局变成拖拽，不用手写 JSON
4. 后续想做 MOD / 自定义关卡是顺带的

**生态确认：**

| 包 | 版本 | 判断 |
|---|---|---|
| **`flame_tiled`** | **3.1.2**（2026-07） | ✅ 官方 monorepo、成熟、版本对齐。**采用** |
| `flame_ldtk` | 0.3.0（2025-10） | ⚠️ LDtk 本身比 Tiled 现代（更好的 API、内嵌实体、auto-layer），但 Flame 侧只有 0.3.0，太年轻。**暂不采用**，后续可重新评估 |

> ⚠️ **修正 v2.2 的一处决策**：原文写的是"明确不用 `flame_tiled`，因为 FE8 地图不是 Tiled 格式"。这个判断**只对了一半**——我们确实**不消费** Tiled 格式，但管线可以**导出成** Tiled。**不消费 ≠ 不导出。** 这个区别很重要，否则 AI 看到那条会以为整条路都不该走。

#### 4.9.3 渲染层：预合成纹理 + 动态图层

GBA 要 4 个 BG 层 + VRAM 瓦片分配 + 硬件滚动寄存器。我们不需要：

```
静态地形  →  管线期预合成成【一张纹理】      运行时就是一个 SpriteComponent
                                                    ↓
动态叠加  →  各自独立的图层，按需绘制
             ├─ 地图变更覆盖（开箱/破墙）—— 只有变更区域需要单独纹理
             ├─ 单位精灵
             ├─ 光标 / 移动范围 / 攻击范围高亮
             ├─ 战争迷雾（shader）
             ├─ 天气（粒子）
             └─ 地图边缘与氛围
```

**运行时零瓦片逻辑。** metatile 组合、调色板 bank、TSA 全部在管线期消化（这正是 §4.3 的语义形式原则）。

**纹理预算**（按章节加载，离开释放）：

| 场景 | 纹理大小 |
|---|---|
| 最大地图，4× 放大 | ~15 MB |
| 典型地图（15×10），4× 放大 | ~3.7 MB |
| 全部 66 张，原生分辨率 | ~27 MB（不需要同时驻留） |

#### 4.9.4 表现升级清单（可选项，逐条评估）

| # | 升级 | GBA 的做法 | 现代做法 | 影响逻辑？ |
|---|---|---|---|---|
| **U1** | **战争迷雾** | `gBmMapFog` 二值 `u8**` 网格 + `RenderBmMapOnBg2()` 盖暗色 BG + `NewBMXFADE` 淡入。**边缘是硬的、有格子感** | Shader 软边视野圈；多单位视野并集；动态过渡（移动时视野渐入）；可选"已探索/当前不可见"两级遮罩 | ❌ 只改表现 |
| **U2** | **天气** | 4 种（`WEATHER_FINE/SNOW/SNOWSTORM/RAIN`），靠瓦片叠加或滚动 | `ParticleSystemComponent`：雪、雨、沙尘、雾 | ❌ 只改表现 |
| **U3** | **瓦片动画** | `graphics/mapanim/` **415 张帧图**，逐帧切瓦片 | Shader 做水面波动/火焰扰动；或打包成图集保留帧动画 | ❌ 只改表现 |
| **U4** | **光照与氛围** | 做不到 | 火把/魔法的局部照明、树与山的地面投影、轻微 AO、边缘景深 | ❌ 只改表现 |
| **U5** | **内建地图编辑器** | 无 | Flutter 内建编辑器（数据模型已有），支持宽屏布局调整与热重载 | ❌ 只改工具 |
| **U6** | 自动接缝 / auto-tiling | 硬边瓦片 | Wang tile 平滑过渡 | ⚠️ **会改变观感**，与"像素高清"风格需对齐，谨慎 |

> ⚠️ **U4 要克制**：战棋游戏里"一眼看清地形和格子"是刚需。氛围不能压过可读性，且必须与已定的 D 混合风格（地图走像素高清，见 §5.3）对齐。

#### 4.9.5 ⭐ 红线：地图数据里混着规则和外观

**这是本节最重要的一张表。** 地图数据不是"一张图"，它是**规则与外观的混合体**：

| 内容 | 能否改 | 为什么 |
|---|---|---|
| **地形类型网格** | ❌ **绝对不能** | 决定移动消耗、回避、防御/魔防加成——这是规则 |
| **地图尺寸与格子坐标** | ❌ **绝对不能** | 单位站位、事件触发坐标、增援位置全部依赖 |
| **天气对移动力的影响** | ❌ **绝对不能** | 实测：`pMovCostTable[0]=普通 / [1]=雨 / [2]=雪` 是**三张不同的表**（`src/masked_08018a60.c`）。天气真的改移动力 |
| **雾战的可见性判定** | ❌ **绝对不能** | 影响 AI 能否看见你、你能否看见敌人（`gBmMapFog` 的读写） |
| **地图变更的触发条件与效果** | ❌ **绝对不能** | 开箱 / 破墙 / 增援是关卡设计本身 |
| 瓦片长什么样、怎么画 | ✅ 随便改 | |
| 雾 / 天气 / 动画的视觉表现 | ✅ 随便升级 | |
| 内部用什么格式存 | ✅ 随便换 | |
| 用什么编辑器 | ✅ 随便换 | |

**判据仍然是 §4.8 那条：逻辑的"做什么"保留，表现的"怎么做"丢弃。**

> **雾战是这条原则的完美案例**：`gBmMapFog` 的**判定**（谁能看见谁）必须逐位一致、由 C Oracle 锁死；但"怎么把这个可见性画出来"可以从"盖一层暗色 BG"升级成 shader 视野。

#### 4.9.6 双格式导出

管线同时产出两种格式，各司其职：

| 格式 | 用途 | 消费方 | 验收 |
|---|---|---|---|
| **紧凑二进制**（地形 u8 网格 + 视觉 u16 网格 + 触发数据） | 运行时 | Dart / Flame | **字节级往返**（§6.2，已实测 `.mar` 无损） |
| **Tiled `.tmx`** | 编辑 / 调试 / 宽屏布局调整 | Tiled + `flame_tiled` | 从 `.tmx` 反向导出必须与二进制一致（可自动比对） |

**两者由同一个源生成，且必须有往返测试锁死一致性**——否则编辑器改过的地图和运行时用的地图会漂移。

### 5.2 阶段 A：提取

#### 5.2.1 C 数据表 → JSON

**问题**：`src/data/data_characters.c` 长这样：

```c
CONST_DATA struct CharacterData gCharacterData[] = {
    [CHARACTER_EIRIKA - 1] = {
        .nameTextId = 0x199,
        .defaultClass = CLASS_EIRIKA_LORD,
        .affinity = UNIT_AFFIN_LIGHT,
        .baseRanks = { [ITYPE_SWORD] = WPN_EXP_E },
        .growthHP = 70,
        .pSupportData = &SupportData_Eirika,
        .attributes = CA_FEMALE,
    },
    // ... 数百条
};
```

**推荐策略：`gcc -E` 预处理 + `pycparser` 解析 AST。**

```
1. gcc -E -I include -I . data_characters.c
     └─ 展开所有 #include 与宏（CONST_DATA、CHARACTER_EIRIKA、CA_FEMALE...）
2. pycparser 解析为 AST
3. 遍历 AST 提取数组初始化器 → 符号名 + 字段值
4. 枚举常量通过解析 include/constants/*.h 的 enum 定义还原为名称
5. 指针字段（&SupportData_Eirika）转成符号名字符串
6. 输出 JSON
```

**为什么不用 `clang` 编译成可执行文件输出 JSON？** 理论上零漂移更优，但会遇到两个坑：(a) `agbcc` 的头文件是 C89 风格，现代 clang 会有大量警告甚至错误；(b) 指针字段需要 `dlsym` 或手写符号表才能还原成名字。预处理 + AST 路线能自然地保留符号名，且 `pycparser` 对 C89 支持良好。

**兜底**：为少数复杂表（如含嵌套指针的表）单独写针对性解析器，而不是追求一个万能解析器。

**产出格式示例**：

```jsonc
// assets/data/characters.json
{
  "schemaVersion": 1,
  "sourceCommit": "f27d18f1b597dd43481690d105dd518f4face8ef",
  "sourceFile": "src/data/data_characters.c",
  "entries": {
    "CHARACTER_EIRIKA": {
      "index": 1,
      "nameTextId": 409,
      "defaultClass": "CLASS_EIRIKA_LORD",
      "affinity": "UNIT_AFFIN_LIGHT",
      "growth": { "hp": 70, "pow": 40, "skl": 60, "spd": 60, "def": 30, "res": 30, "lck": 60 },
      "baseRanks": { "ITYPE_SWORD": "WPN_EXP_E" },
      "attributes": ["CA_FEMALE"],
      "supportData": "SupportData_Eirika"
    }
  }
}
```

> **`sourceCommit` 字段是必须的。** 上游仓库每天更新。没有版本锚点就无法定位"某个数值什么时候变了"，也无法在 M1 之后安全地重跑管线。

#### 5.2.2 地图

FE8 的地图数据分五层，缺一不可：

| 层 | 来源 | 转换 |
|---|---|---|
| **瓦片索引网格** | `graphics/map/layout/*.mar` | 每格 2 字节。**已实测转换公式见下** |
| **尺寸元数据** | `graphics/map/layout/*.json` | `{"id":"PrologueMap","width":15,"height":10}` |
| **metatile 定义** | `graphics/map/TileConfiguration{1..10}.S` + `tile_config.inc` | 1024 个 metatile，每个 = TL/TR/BL/BR 四个角瓦片，形式为 `metatile 0x01DF, 0x05DF, 0x01FF, 0x05FF` |
| **瓦片图形** | `graphics/map/ObjectType{4..10}.png` + `TowerOfValniObjectType.png` | 索引 PNG（4bpp） |
| **调色板** | `graphics/map/MapPalette{1..19}.pal` + 专用调色板 | JASC 文本格式 |
| **地形** | metatile → `TERRAIN_*` 的映射表 | 见下 |

**`.mar` 转换公式（已从 `scripts/mar_to_map.py` 实测确认）：**

```python
# 输入：.mar 原始字节 + 同名 .json 的 width/height
# 输出：byte[0]=width, byte[1]=height, 随后 width*height 个小端 u16
for i in range(0, len(marData), 2):
    raw = int.from_bytes([marData[i+1], marData[i]], byteorder="big")  # = 小端 u16
    tile = (raw >> 3) & 0xFFFF                                        # 有效瓦片索引
    out += tile.to_bytes(2, byteorder="little")
```

即 **`tile = u16_le(mar, offset) >> 3`**，输出为 `[width, height] + 小端 u16 数组`。
（参考实现基于 FEBuilderGBA 的 `MapEditorForm.cs#L1293`。）

**章节与地图的关联**在 `src/data/chapter_settings.h` 的 `gChapterDataTable[]`（79 章）：

```c
{
    .internalName = "L00",
    .map = {
        .obj1Id = 1, .obj2Id = 0, .paletteId = 2, .tileConfigId = 3,
        .mainLayerId = 4, .objAnimId = 5, .paletteAnimId = 0, .changeLayerId = 6,
    },
    .initialFogLevel = 0, .hasPrepScreen = FALSE,
    .initialPosX = 1, .initialPosY = 0, .initialWeather = WEATHER_FINE,
    // ...
}
```

**地图变更**在 `src/data/*MapChanges_ref/`，结构是「矩形 + 替换瓦片块」：

```
.byte id, x, y, w, h, 0, 0, 0
.word <替换瓦片数组符号>
...
.word 0xff, 0, 0        ← 终止符
```

**产出格式（双格式，详见 §4.9.6）**：

```jsonc
// ① 运行时：紧凑二进制 + 元数据
// assets/maps/PrologueMap.json
{
  "id": "PrologueMap",
  "width": 15, "height": 10,
  "tileset": "ObjectType4",
  "palette": "MapPalette1",
  "tileConfig": "TileConfiguration1",
  "tileGrid": "PrologueMap.tiles.bin",        // u16 LE × 150
  "terrainGrid": "PrologueMap.terrain.bin",   // u8 × 150（管线预计算）
  "composite": "PrologueMap.composite.png",   // 预合成纹理（§4.9.3）
  "mapChanges": [
    { "id": 3, "x": 4, "y": 2, "w": 3, "h": 2, "tiles": "Ch1_change_1.bin" }
  ]
}

// ② 编辑/调试：Tiled .tmx（同一源生成，往返一致性由测试锁死）
// assets/maps/tiled/PrologueMap.tmx
```

> ⚠️ **两种格式必须来自同一个源，且要有往返测试**（`.tmx` → 二进制 必须与直接产出的一致）。否则编辑器改过的地图和运行时用的地图会漂移。

> **关键决策：地形网格在管线里预计算。**
>
> 原版是运行时推导（metatile → `gTilesetTerrainLookup` → 地形 ID）。我们**预计算好，直接导出 `terrainGrid`**。
>
> 理由：地形推导每张图只发生一次，运行时重复计算没有收益；预计算后 `core/map/` 只需读一个 u8 数组，简化逻辑层，也让调试更直观。代价是地图变更引起的地形变化需要在管线里一并导出（变更后的地形）。

#### 5.2.3 事件脚本

输入是 `src/data/EventScr_*_ref/*.c` 里的 EA 宏调用序列，需要解析成 JSON。

**解析要点：**

- 宏无分号结尾（特例是 `#define EVENT_WORD` 那两行转义宏，需跳过 `#define` 与注释）
- 枚举参数（`EVT_SLOT_2`）需从 `include/constants/` 还原
- 宏定义在 `include/EAstdlib.h`（10852 字节），解析其 `#define` 即可知道每个宏的参数个数
- 引用其他脚本的 `CALL(label)` 需要建立符号引用

```jsonc
// assets/events/Ch10A_0.json
{
  "label": "EventScr_Ch10A_0",
  "chapter": "Ch10A",
  "ops": [
    { "op": "CAMERA_CAHR", "args": [79] },
    { "op": "STAL", "args": [60] },
    { "op": "CURE" },
    { "op": "MUSC", "args": [20] },
    { "op": "TEXTSHOW", "args": [2545] },
    { "op": "TEXTEND" },
    { "op": "SVAL", "args": ["EVT_SLOT_2", 19] },
    { "op": "CALL", "args": ["Event_TextWithBG"] },
    { "op": "EVBIT_T", "args": [7] },
    { "op": "ENDA" }
  ]
}
```

**同时要导出的事件触发表**：章节事件由 7 类触发源驱动（§4.5），这些表也在 `src/data/` 中，需要一并提取。

> **⭐ 一个额外的验证机会**：官方 `FireEmblemUniverse/fireemblem8u`（219★，活跃）把同样的事件脚本以 `src/events/ch1-eventscript.h` 的形式存在。虽然 JP/US 有差异，但事件**结构**高度一致。可以用它来**验证我们的事件脚本解析器是否正确**——如果解析器能从 8j 的数据里还原出与 8u 同构的宏序列，说明解析正确。

#### 5.2.4 文本

`texts/jp_texts.txt` 已是明文，不需要 Huffman 解码。

```
#0x0006
マップビューア
#0x0007
顔ビューア
```

**控制码处理**：`texts/jp_textdefs.txt`（997 字节）定义了控制 token 名 → u16 值的映射。带控制码的消息需解析成结构化 token 序列，而不是当普通字符串：

```jsonc
{ "232": { "tokens": [
    { "t": "LoadFace", "args": [3] },
    { "t": "text", "v": "エイリーク" },
    { "t": "NL" },
    { "t": "text", "v": "……そう。" },
    { "t": "X" }
] } }
```

#### 5.3.2 立绘管线（混合风格的重点）

**关键发现：原版立绘不是一张插画，而是瓦片集。**

```
portrait_Eirika_tileset.png       ← 瓦片集（不是完整图！）
portrait_Eirika_mouth.png         ← 嘴部帧
portrait_Eirika_chibi.png         ← 小头像
portrait_Eirika_palette.agbpal    ← 调色板
portrait_Eirika_flashback_palette.agbpal
```

所以不能直接"AI 重绘 `portrait_Eirika_tileset.png`"——那是一个瓦片图集，不是一张人脸。

**正确的管线（体现 §4.3 语义形式原则）：**

```
1. 提取：瓦片集 + TSA + 调色板  ──拼合──▶  一张完整立绘 PNG（语义形式）
2. 重绘：完整立绘 PNG  ──AI img2img / 超分 / 重绘──▶  高分辨率现代插画
3. 表情：嘴部帧原样保留或重新生成（2 帧嘴型，简单）
4. 引擎：直接渲染完整立绘 + 嘴部叠加（不再需要瓦片/TSA）
5. 换色：阵营色/回忆模式 用 shader 实现（不再需要调色板切换）
```

**自动校验（无需人工）**：

- 拼合后的图像尺寸与 TSA 声明一致
- 重绘后图像尺寸符合预期倍率
- Alpha 通道存在且边缘合理（非全不透明）
- 调色板主色分布与原图的 L2 距离在阈值内（防止 AI 跑偏成完全不同的色调）
- 嘴部区域的位置坐标与主图对齐（可用特征点检测）

**这一步是整个美术管线的技术验证点**，建议在 M11 先做 3–5 个角色的端到端验证。

#### 5.3.3 战斗动画（banim）方案

这是美术部分风险最高的子系统，但我实测后发现它**比预想的友好得多**。

**格式实测结果：**

`banim/` 目录下 201 个 `*_motion.s`，每个定义一套战斗动画。格式（来自 `include/banim_code_frame.inc`）：

```asm
.macro banim_frame_oam attr0, attr1, attr2, dx, dy
    .hword \attr0, \attr1, \attr2, \dx, \dy, 0
.endm

.macro banim_frame_affine pa, pb, pcc, pd, total=0
    .hword \total
    .if \total
        .hword 0xFFFF
    .else
        .hword 0
    .endif
    .hword \pa, \pb, \pcc, \pd
.endm

.macro banim_frame_end
    .word 1, 0, 0
.endm
```

实际数据（`banim/banim_armm_sp1_motion.s`）：

```asm
banim_armm_sp1_oam_frame_0_l:
	banim_frame_oam 0x0,    0x9000, 0x81, -22, -16
	banim_frame_oam 0x4000, 0x5000, 0x61, -22, -24
	banim_frame_oam 0x8000, 0x5000, 0x80,  10, -16
	banim_frame_oam 0x0,    0x1000, 0x60, -30, -22
	banim_frame_oam 0x0,    0x5000, 0x20,  18,   0
	banim_frame_end
```

对应的资源（`graphics/banim/`）：

```
banim_armm_sp1_sheet_0.png       ← 瓦片图集
banim_armm_sp1_sheet_1.png
banim_armm_sp1_sheet_2.png
banim_armm_sp1.agbpal            ← 调色板
banim_armm_sp1_2.agbpal          ← 阵营色变体
banim_armm_sp1_3.agbpal
banim_armm_sp1_4.agbpal
```

**关键结论：**

1. 帧不是位图，而是**一组 OAM 条目**（`attr0, attr1, tile索引, dx, dy`）
2. **`dx` / `dy` 是像素偏移**（-22, -16 这样的有符号值）
3. `attr2` 是**图集内的瓦片索引**
4. 每套动画有左右朝向（`_l` / `_r`）和多套调色板（阵营色）
5. 每个帧序列以 `banim_frame_end` 终止，还支持 `banim_frame_affine` 做旋转缩放

**三种重绘策略的评估：**

| 策略 | 做法 | 会坏什么 | 工作量 | 风险 | 结论 |
|---|---|---|---|---|---|
| **S1 整数放大 + 坐标乘法** ⭐ | 图集整体 2× 放大；所有 `dx`/`dy` 乘以 2 | 什么都不坏。整数倍放大不改变瓦片结构，坐标线性缩放即可 | **极低（脚本可全自动）** | **极低** | **基线方案，必做** |
| **S2 AI 重绘图集内容** | 保持图集布局与瓦片索引不变，只重绘每个瓦片的像素内容 | 若 AI 破坏 8×8 网格对齐则穿帮；需强制网格约束 | 中 | 中 | **在 S1 之上叠加，作为可选精修** |
| **S3 重新制作为骨骼/序列帧** | 抛弃 OAM 数据，在新引擎里重新设计动画 | 丢失原版时序、位移、特效节奏；2282 个文件全部重做 | 极高 | 极高 | **不做** |

**推荐：S1 打底 + S2 可选精修。**

S1 的完整流程是一个纯机械变换，**可以完全自动化且自动验证**：

```
输入：banim_armm_sp1_sheet_{0,1,2}.png  +  banim_armm_sp1_motion.s
变换：1. 图集每张 2×（最近邻或像素画专用放大模型，必须保持 2×2 块结构）
      2. 解析 *.s 中所有 banim_frame_oam 的 dx/dy，乘以 2
      3. 调色板不变（若转 RGBA 则用 shader 复现阵营色）
      4. attr0/attr1/attr2 不变（tile 索引不变，因为图集是整体等比放大，
         但 GBA 的 tile 是 8×8，2× 后每个 tile 变 16×16 —— 需要重新排布图集，
         因为一个 8×8 tile 变成 2×2 个 tile，索引要重映射）
输出：放大后的图集 + 变换后的 OAM 数据
```

> ⚠️ **必须注意的一个技术细节**：GBA 的 `attr2` 是图集内的瓦片索引（每瓦片 8×8）。2× 放大后，原来的一个 8×8 瓦片变成 16×16 像素，在 GBA 语义里等于 2×2 个瓦片。因此**图集不能简单整体放大**——必须重新组织瓦片索引映射（`newIndex = remap(oldIndex)`），或者——**更简单的做法**——新引擎根本不使用 GBA 的瓦片语义，而是把图集当作**普通 RGBA 纹理**，OAM 条目当作**带源矩形的位置描述**。这样 2× 放大只需要坐标乘 2，没有索引重映射问题。
>
> 这正是 §4.3 语义形式原则的价值：**把 GBA 的瓦片语义在提取阶段消化掉，引擎层只看到"纹理 + 源矩形 + 目标位置"**，一切就变得平凡了。

**自动校验（无需人工）：**

- 放大后图集尺寸 == 原尺寸 × 2
- 所有 OAM 的源矩形在纹理范围内
- 帧数、帧内 OAM 条目数、帧序与原始一致
- 渲染任意帧的截图与原版同帧截图做**结构相似度比对**（放大后的轮廓应与原版一致）

## 6. 验证体系（零人工判定的核心）

**这是本方案最重要的章节。** 没有它，"AI 生成 + AI 测试"就是空话。

（v2.1 变更）原方案依赖"Oracle ROM + mGBA Golden Trace"做整机验证，现已**移除**（决策 D13）。替代方案是下面 §6.2 的**字节级往返验证**——它不需要 ROM，而且是更严格的判定。
>
> **C Oracle 不受影响**（它本来就不需要 ROM），并且已经**实测验证可行**（§6.3）。

### 6.1 五层验证金字塔

| 层 | 名称 | 判定对象 | 手段 | 运行频率 | 覆盖 |
|---|---|---|---|---|---|
| **L0** | 数据提取正确性 | 提取产物 | **字节级往返**（§6.2）+ schema + 条数 | 每次管线运行 | 全部数据资产 |
| **L1** | 单元测试 | 单个函数 | `dart test` + 边界值 + 不变量 | 每次保存 | 全部 core 函数 |
| **L2** | **C Oracle 对照** | 函数行为 | host 编译真实反编译 C，比对输出（§6.3） | CI | 公式、算法、AI 评分、寻路 |
| **L3** | **静态契约** | 跨操作的顺序/时序 | 乱数消耗序表 + 事件状态机回放（§6.4） | CI | 被 Golden Trace 覆盖的那部分 |
| **L4** | 视觉验证 | 渲染输出 | Python 参考渲染器 diff + 多模态视觉判定（§6.5） | CI | 地图、UI、动画 |

**L0 + L2 是硬判定（字节级/逐位级），L3 是中等强度，L4 是结构级。** 这套组合不依赖原始 ROM。

**为什么 L0 的"字节级往返"能替代 Golden Trace 的大部分价值：**

```
反编译项目的 CI 已经证明：   源码 ──────▶ ROM        字节一致 ✓
我们的管线做：              源码 ──▶ 内部格式 ──▶ 重新序列化 ──▶ 源码'
若 源码' == 源码，则内部格式忠实于源码，传递性地也就忠实于 ROM。
```

**这是传递性证明，不需要碰任何 ROM 文件。** 而且它验证的正是我们真正消费的东西。

### 6.2 ⭐ L0：字节级往返验证

**对每一类数据资产，构造"解析 → 内部形式 → 重新序列化 → 与原文件逐字节比对"的闭环。**

| 资产 | 往返链路 | 状态 |
|---|---|---|
| **地图 `.mar`** | `.mar` → u16 瓦片网格 → 重新编码 → `.mar` | ✅ **已实测无损**（§6.2.1） |
| **文本** | `jp_texts.txt` → token 序列 → 重新序列化 | ✅ 格式被上游**主动设计为可往返** |
| **C 数据表** | `.c` → JSON → 重新生成 C 字面量 → 与源文本比对 | 待实现 |
| **瓦片配置 `.S`** | `.S` → metatile 表 → 重新生成 → 比对 | 待实现 |
| **事件脚本** | `.c` 宏序列 → JSON → 重新生成 → 比对 | 待实现 |
| **立绘/图集** | PNG → 语义形式 → 重新编码 PNG → 像素比对 | 待实现 |
| **音乐** | MIDI → OGG（单向，无法往返） | 用时长/结构校验替代 |

#### 6.2.1 已验证：`.mar` 往返是无损的

对全部 66 张地图的 **26541 个瓦片值**做了实测：

```
低 3 位分布: {0: 26541}        ← 全部为 0，所以 raw >> 3 可精确逆运算
尺寸校验:   len(.mar) == width × height × 2   全部满足
```

因此 `tile = u16_le(mar, i*2) >> 3` 与 `raw = tile << 3` 互为逆运算。**地图提取的正确性可以做到字节级证明。**

#### 6.2.2 上游已为往返做好了设计

`texts/jp_textdefs.txt` 的原文注释：

> *"Maps a `[Token]` name to one or more u16 symbol values. [...] multi-value / face-control sequences are dumped as raw `[$XXXX]` tokens instead, **so the round-trip stays unambiguous**."*

134 种控制码，多值序列用 `[$XXXX]` 原始转义保证无歧义。反编译项目自己的 `make text-verify` 就是这个思路。**我们可以直接复用其设计。**

#### 6.2.3 往返测试的实现要求

- **每条往返链必须是一个可独立运行的命令**，输出 `PASS` / `FAIL` + 首个不一致的偏移
- **失败必须能定位**：报告"第 N 个元素、字段 X、期望 vs 实际"
- **产物大小写进断言**：例如"瓦片数 == width × height"，不一致立刻报错

#### 6.3.3 ⚠️ 已知限制：64 位指针导致结构体布局不同

`struct Unit` 含 3 个指针，host 上每个占 8 字节（GBA 是 4 字节）：

| | host (arm64) | GBA (armv4t) |
|---|---:|---:|
| `sizeof(struct Unit)` | **88** | **72** |
| `offsetof(Unit, def)` | **0x1F** | **0x17** |
| `offsetof(Unit, items)` | 0x26 | 0x1E |

**不影响绝大多数逻辑函数**：只要函数用命名字段访问，host 侧的自洽布局就给出与 GBA 相同的**逻辑结果**（上面的 `GetUnitDefense` 就是证明）。

**影响少数函数**：直接对结构体 `memcpy`、按硬编码偏移做指针运算、或处理存档原始块的函数。

**对策**：把这类函数标记为 `ORACLE_UNSUPPORTED`，在 frontier 里单独列出，改用代码审查验证。

> **后路**：若日后需要严格布局，`zig cc --target=wasm32-wasi` 提供 32 位指针 + 可移植运行。
> 已验证不可行的：`clang -m32`（macOS 已移除 32 位支持）、`clang --target=wasm32`（缺 sysroot/libc）。

#### 6.3.4 构建要求

- **必须 `-O2`**：上游 agbcc 在 `-O2` 下编译，GNU89 的 `extern inline`（同一函数在多个文件中重复定义）依赖内联消除。`-O0` 会符号未定义。
- **必须 `-std=gnu89`**：C99 的 `extern inline` 语义相反（会产出外部定义），多 TU 链接时符号冲突。

**⭐ `crosscheck.py` 是不能省的一环。** C Oracle 用的数值是权威的，但 **harness 管道可能写错**（struct 字段填错位、TSV 解析错、类型截断没模拟对）。这些错误会让 Oracle **安静地给出错误的期望值**，Dart 侧"老实对齐"就会一起错。`crosscheck.py` 从 C 源码独立重写一遍逻辑逐条比对，两者一致才说明管道是通的。

> 它同时是 **Dart 侧实现的预演**——Dart 移植会遇到完全相同的整数截断问题（`s8`/`s16`/`u16`，以及 C 的 `%` 向零截断 vs Dart 的向下取整）。

**新增场景的步骤**（详见 `tools/oracle/README.md`）：挑依赖浅、有分支边界的函数 → 写 `scenarios/<名>.c` 只实现 `oracle_run` → 写 `.deps` 列出反编译源文件 → 在 `gen_vectors.py` 加**手工边界用例**（随机几乎不会命中边界）→ 在 `crosscheck.py` 加独立实现 → `run_all.sh` 生成 golden → `verify.sh` 确认全绿。

**向量覆盖要求：**

- **必须包含手工边界用例**，不能只有随机值
- **必须覆盖乱数消耗**：不只公式结果一致，**乱数消耗的次数和顺序**也必须一致
- **固定 seed**：向量与 golden 都提交到仓库，保证可复现

### 6.4 L3：静态契约（替代 Golden Trace）

Golden Trace 原本覆盖"跨操作的时序与涌现行为"。移除后，这部分改用**从 C 源码静态提取的契约**。

#### 6.4.1 乱数消耗顺序契约

这是最容易出错、也最危险的地方——**乱数消耗错一位，后面全部错位**。

**做法**：从 C 源码静态提取所有乱数调用点，建立显式的契约表。

```bash
# 扫描全部 NextRN* / Roll1RN / Roll2RN 调用点
grep -rn "NextRN\|Roll1RN\|Roll2RN" third_party/fireemblem8j/src/*.c
```

产出：

```jsonc
// docs/rng-contract.json
{
  "note": "从 C 源码静态提取。每个操作消耗的乱数次数与顺序。",
  "operations": {
    "AttackHitRoll":   { "consumes": [{"fn": "Roll2RN", "count": 1}], "source": "src/BattleGenerateReal.c:NN" },
    "AttackCritRoll":  { "consumes": [{"fn": "Roll2RN", "count": 1}], "source": "..." },
    "LevelUpGrowth":   { "consumes": [{"fn": "NextRN_100", "count": 7}], "source": "..." }
  }
}
```

Dart 侧的乱数模块必须实现一个**可断言的消耗追踪器**：

```dart
class Rng {
  final List<int> seeds;
  int get consumed => _consumed;   // 测试断言用
  int nextRn() { _consumed++; ... }
}
```

测试断言"某个操作序列消耗的乱数次数与顺序 == 契约表"。

**强度评估**：比 Golden Trace 弱（契约来自静态阅读，可能有遗漏），但比没有强得多，且**完全可自动化**。

#### 6.4.2 事件引擎状态机回放

事件脚本是**数据**（`src/data/EventScr_*_ref/`），解释器语义来自 `src/event.c`（可由 C Oracle 覆盖单个 opcode）。

对整章流程，用**状态机回放测试**：把脚本 JSON 喂给 Dart 事件引擎，断言：

- 每步的 opcode、槽位值、调用栈深度符合预期
- 任意步存档 → 读档 → 续跑，状态完全一致（这是显式状态机设计的直接收益）
- `CALL` / `BRANCH` / `GOTO` 的目标标签都存在

### 6.5 L4：视觉验证

**已实测确认：本环境具备多模态图像理解能力**（能读取并描述 PNG 内容）。这让视觉验证可以从"纯几何断言"升级为真正的视觉判定。

#### 6.5.1 双轨验证

| 轨道 | 方法 | 判定强度 |
|---|---|---|
| **结构轨** | 尺寸、网格对齐、调色板条目数、alpha 通道、帧数、引用完整性 | 硬断言，CI 阻塞 |
| **视觉轨** | 与参考渲染器对比、多批次风格一致性、原版素材相似度 | 软判定，低于阈值告警 |

#### 6.5.2 Python 参考渲染器（替代原版截图比对）

原方案用 mGBA 截图做像素 diff，现已移除。替代方案：

**用 Python 独立实现一套 GBA BG 渲染语义**（公开文档化的行为：4bpp 瓦片、16 色板、metatile 合成、图层顺序），从**同一份提取产物**渲染出参考图，再与 Flame 的输出比对。

它能验证：

- ✅ **提取管线正确**（两侧消费同一份 JSON，若提取错了双方都会错——所以还要配合 §6.2 的往返验证）
- ✅ **Flame 渲染器忠实于规范**（与一份独立实现对比）
- ❌ 不能验证"与原版游戏实际画面一致"

**重要的是**：GBA 的 BG 渲染语义是**完全由数据决定**的。如果 (a) 提取正确（往返证明）且 (b) 渲染器符合规范（参考渲染器证明），那么输出**就是**原版的画面。风险被这两条覆盖了。

#### 6.5.3 多模态视觉判定的用途

主要用于**AI 重绘的质量把关**（因为这里没有客观函数）：

- 同一角色的多个表情是否风格统一
- 立绘重绘后与原版的色调分布是否偏离过大
- 地图瓦片集放大后接缝是否正常
- 批量生成后的异常检出（挑出明显崩坏的图）

**这些是软判定，用于告警与筛选，不作为 CI 阻塞条件。**

## 7. ⭐ AI 驱动开发工作流

这一章回答"怎么做到尽量不人工"。设计直接借鉴 `third_party/fireemblem8j/.claude/` 里经过实战验证的自主开发流程。

### 7.1 核心原则

| 原则 | 含义 |
|---|---|
| **参照物优先** | 每个任务都必须有明确的 C/日文/原图参照物。没有参照物的任务不允许进入队列 |
| **机器判定** | 每个任务的验收必须是一条命令。不存在"我觉得对了" |
| **冷启动认证** | 只有集成者的完整验证运行能认证完成。生产者不能自我认证 |
| **小步前进** | 一个任务 = 一个可独立验证的增量。原子提交 |
| **永不红灯** | 硬不变量必须始终绿。红了就回退，不修复 |
| **卡死就换** | 同一方法失败两次 → 换任务，不在同一面墙上撞 |

### 7.2 智能体拓扑

**借鉴点**：`fireemblem8j` 的 `.claude/agents/README.md` 有一个关键洞察——**并行安全的前提是"一个构建树 + 一个 git index + 唯一的全量验证 oracle"**。朴素的并行会破坏它。

所以分工必须按"是否写共享状态"来切：

| 角色 | 职责 | 写权限 | 并行度 |
|---|---|---|---|
| **`port-researcher`** | 读 C 源码 + 依赖链，产出**移植配方**（含边界条件、陷阱、依赖符号） | **只读** | 大量并行 |
| **`port-worker`** | 在自己独立的 git worktree 里移植一个函数/TU，跑本地测试 | 自己的 worktree | 并行（独立目标） |
| **`port-integrator`** | **单例**。合并分支、跑完整 `run_all.dart`、提交。唯一有权写入主分支的角色 | 共享树（持锁） | **不可并行** |
| **`oracle-verifier`** | 对抗性验证：尝试**反驳**"Dart 实现等价于 C"的声明 | **只读** | 大量并行 |
| **`data-extractor`** | 数据管线（C 表 → JSON、地图解析等） | 只写 `tools/` + `assets/` | 并行 |
| **`art-pipeline`** | 美术重绘批处理 | 只写 `assets/graphics/` | 并行 |

**关键规则（直接照搬 decomp 的教训）：**

> **一个子智能体永远不能自我认证。** 只有 `port-integrator` 的冷启动完整 `run_all.dart` 才能认证一个移植。这是"权力分立"（harness integrity）——生产者和认证者必须是不同的角色。

`port-integrator` 通过文件锁保证单例（同一时刻只能有一个），第二个实例启动时失败退出。

### 7.3 任务单元设计

**这是 AI 驱动效率的关键。**

⭐⭐ **但在切分之前，必须先按 §4.8 的不移植清单筛一遍。** 反编译项目有 8692 个函数，如果任务派发时只说"移植 FE8"，AI 会平均地对待它们，把大量时间花在注定被丢弃的 GBA 平台代码上。

```
第一步（筛选）：C 源文件是否命中 §4.8 的 N1–N10？
   命中 → 默认不派发（除非配方里明确解释了为什么需要）
   未命中 → 进入第二步

第二步（分类）：
   规则层   → 派发"移植"任务（有 C Oracle 验收）
   表现层   → 派发"重写"任务（有结构断言 + 视觉验收，没有唯一正确答案）
   数据层   → 派发"提取"任务（有字节级往返验收）
```

**三类任务的性质完全不同，不能混为一谈：**

| 任务类型 | 输入 | 产出 | 验收 | 能否自动判定"对" |
|---|---|---|---|---|
| **移植**（规则层） | C 源码 | Dart 函数 | **C Oracle 逐位对照** | ✅ 能，有唯一正确答案 |
| **提取**（数据层） | 原版数据文件 | JSON / 二进制 + 解析器 | **字节级往返** | ✅ 能，有唯一正确答案 |
| **重写**（表现层） | 原版作为参考 + 设计规范 | Flutter/Flame 组件 | 结构断言 + 视觉判定 | ⚠️ **不能完全**，是设计工作 |

> **表现层任务是本方案里唯一"没有唯一正确答案"的部分。** 它不应该被派成"移植 `ProcScr_xxx`"（那会产出大量垃圾），而应被派成"实现一个屏幕闪白效果，参数：持续 160ms，颜色 #FFFFFF"。
>
> 原版代码在这类任务里的作用是**提供信息结构与时序参数**（§4.8.3），不是提供实现。

**规则层任务单元定义**：

```
一个移植任务 = (C 源文件, 目标 Dart 文件, 依赖符号列表, Oracle 场景, 验收命令)
```

**映射规则**：保持文件路径的可追溯性。

```
src/GetUnitDefense.c          →  lib/core/rules/get_unit_defense.dart
src/AiAttemptBallistaCombat.c →  lib/core/ai/ai_attempt_ballista_combat.dart
src/NextRN.c                  →  lib/core/rng/next_rn.dart
```

**每个 Dart 文件必须带一个来源注释头**（lint 强制）：

```dart
// PORT OF: third_party/fireemblem8j/src/GetUnitDefense.c
// SOURCE COMMIT: f27d18f1b597dd43481690d105dd518f4face8ef
// ORACLE: test/golden/get_unit_defense.jsonl
// STATUS: verified
```

**收益**：

1. **并行安全**：不同任务写不同文件，不会冲突

### 7.6 卡死检测与升级规则

**直接照搬 decomp 的规则：**

| 情况 | 动作 |
|---|---|
| 同一方法失败 **2 次** | 记录阻塞点，**切换任务**。不在同一面墙上撞 |
| 一个"杠杆"（方法）连续产出为 0 达 **2 小时** | 标记为 `EXHAUSTED`，写入决策日志，不再派发该类任务 |
| 某个任务连续失败 **3 轮** | 标记 `BLOCKED`，附上具体阻塞条件，移到 P2 |
| 硬不变量无法恢复 | 回退本次改动 |

**`EXHAUSTED` 机制很重要**：它防止整个系统反复尝试一个已经证明无效的方法。由 `tools/progress/wave_status.dart` 追踪。

### 7.7 决策日志

`docs/decisions.md`，每条决策一个编号（`D1`、`D2`...）：

```markdown
## D3: 事件引擎用显式状态机而非 async/await
**日期**: 2026-10-05
**背景**: 需要支持"对话播放中存档"
**决策**: 事件引擎实现为显式状态机，所有中间状态可序列化
**理由**: Dart 的 async/await 状态无法序列化；显式状态机还便于 AI 调试（可 dump）
**影响**: 事件引擎的所有实现必须遵循此模型；复杂度略高但换来了可存档性
**状态**: 生效
```

**AI 在遇到分叉时应自主决策并写日志，而不是停下来问人**（照搬 decomp 的规则）。只有在真正不可逆或超出授权时才升级给人。

### 7.8 失败模式与对策

| 失败模式 | 症状 | 对策 |
|---|---|---|
| **AI 自我认证** | 智能体声称"已完成"，但 Oracle 不通过 | 生产/认证角色分离；只有 integrator 能认证 |
| **并行污染** | 多个 worker 同时改共享文件，互相覆盖 | worktree 隔离 + 单例 integrator + 文件锁 |
| **上下文爆炸** | 单个任务太大，AI 读不完依赖 | 任务粒度 = 一个函数；`port-researcher` 预先压缩依赖信息 |
| **在错误的墙上撞** | 反复尝试同一个不可行的方法 | 失败 2 次即换任务；`EXHAUSTED` 机制 |
| **假进度** | 移植文件数涨了但都不能跑 | 三个维度同时度量；只有"章节可玩"算真进度 |
| **风格漂移** | 不同 AI 产出的 Dart 风格差异大 | 先手工移植 5 个"风格锚点"文件；lint 强制；模板化 |
| **静默回归** | 新改动破坏了旧功能但没人发现 | 硬不变量必须全量跑（不是增量）；原子提交便于二分定位 |

## 附录 B：术语表

| 术语 | 含义 |
|---|---|
| **decomp** | Decompilation，反编译项目。通过匹配编译验证还原出与原 ROM 字节一致的源代码 |
| **matching C** | 能被编译器编译出与原 ROM 完全相同的机器码的 C 代码 |
| **pret** | 著名的 GBA 反编译社区项目族（pokeemerald、pokefirered 等），FE 的 decomp 沿用其工具链 |
| **EA / Event Assembler** | 火焰纹章 ROM 修改社区的事件脚本宏语言 |
| **banim** | Battle Animation，战斗动画（图集 + OAM 脚本） |
| **opanim** | 转职/升级动画 |
| **TSA / metatile** | FE8 地图由 metatile 组成，每个 metatile = 2×2 个 8×8 瓦片 |
| **OAM** | Object Attribute Memory，GBA 的精灵属性表（位置/瓦片/调色板/翻转） |
| **Oracle** | 标准答案机。本项目中指 **C Oracle**：在开发机上编译反编译的 C 代码，作为 Dart 实现的判卷标准（§6.3） |
| **往返验证** | 源码 → 内部格式 → 重新序列化 → 与原文件逐字节比对。因反编译 CI 已证明源码 ≡ ROM，往返一致即传递性地证明与原版一致（§6.2） |
| ~~Golden Trace~~ | 原方案中让原版 ROM 在模拟器里跑、比对内部状态的做法，**已移除**（D13） |
| **硬不变量** | 必须始终为真的断言。本项目 = `run_all.dart` 输出 ALL GREEN |
| **Frontier** | 唯一的工作清单文档（`docs/frontier.md`），机器生成 |
| **2RN** | FE 的命中判定机制，取两个随机数取平均 |
| **语义形式** | 剥掉 GBA 硬件约束后的资源表示（完整立绘 / 动画剪辑 / 地形图），引擎只消费它 |
| **worktree 隔离** | 每个并行 worker 在独立的 git worktree 里工作，避免污染共享状态 |
